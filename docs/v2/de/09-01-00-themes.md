# Das Templatesystem
Als Templatesystem kommt smarty zum Einsatz.
Wer ein eigenes Template erstellen möchte, sollte sich also zunächst mit der smarty Dokumentation
vertraut machen.

## Gut zu wissen

* Alle Themes befinden sich im Verzeichnis `/public/assets/themes/`.
* Die Themes `administration` und `default` werden bei jedem Update überschrieben.
* Themes können den Funktionsumfang von SwiftyEdit erweitern

## Verzeichnisstruktur

* themes/theme-name/
    * dist/ (__erforderlich__: SwiftyEdits Templates verlinken diese Dateien direkt namentlich,
      siehe [Theme-Assets bauen](#theme-assets-bauen) dazu, wie sie dort hineinkommen)
        * default.css, theme.js
        * editor.css, tinyMCE_config.js (siehe [tinyMCE](#tinymce))
        * fonts/ (nur falls Dein CSS sie braucht, z. B. die Bootstrap-Icons-Webfonts des
          Standard-Themes)
    * src/ (optional - nur vorhanden, wenn Du Deine Assets aus Quelldateien baust; das
      `default`-Theme macht das mit Vite, siehe [Theme-Assets bauen](#theme-assets-bauen))
        * scss/ (Sass-Partials, Einstiegspunkt `default.scss`)
        * js/ (JS-Einstiegspunkt `frontend.js` und `js/components/`)
        * editor.css, tinyMCE_config.js (siehe [tinyMCE](#tinymce))
    * images/ (Vorschaubild, Icon usw. - werden in der Theme-Auswahl angezeigt)
    * docs/ (optional, Deine eigene Theme-Dokumentation)
    * php/
        * index.php (allgemeine Theme-Funktionen, nur Frontend)
        * options.php (optional) verwaltet Theme-Optionen (Frontend und Backend)
        * xhr.php (optional) XHR-Routing-Datei (Frontend), siehe [Theme-XHR-Endpunkt](#theme-xhr-endpunkt)
        * page-values.php / category-values.php (optional), siehe [Zusätzliche Daten schreiben](#zusaetzliche-daten-schreiben-php)
    * templates/ (Deine Smarty-Template-Dateien, siehe [Templates](09-01-01-templates.md))
    * templates-mail/ (Deine Mail-Templates, siehe [Mail-Templates](09-01-01-templates.md#mail-templates))
    * package.json, vite.config.js (optional - nur falls Du wie das `default`-Theme mit Vite
      baust, siehe [Theme-Assets bauen](#theme-assets-bauen))
    * info.xml (Theme-Manifest: Name, Version, Lizenz, Autor, benötigte Core-Version)
    * readme.md (optional, wird im ACP-Theme-Editor und Doku-Browser geparst angezeigt)

## Theme-Assets bauen {#theme-assets-bauen}

SwiftyEdit ist es egal, wie die Dateien in `dist/` entstanden sind - wichtig ist nur, dass sie
unter den erwarteten Namen existieren. `head.tpl` verlinkt `dist/default.css` und
`dist/theme.js` direkt (und `maintenance.tpl` macht dasselbe für `default`), und die
tinyMCE-Integration erwartet `dist/editor.css` und `dist/tinyMCE_config.js` (siehe
[tinyMCE](#tinymce)). Über diesen Datei-/Verzeichnis-Vertrag hinaus ist der Einsatz eines
Build-Tools komplett optional: Du kannst reines CSS und JS von Hand direkt nach `dist/`
schreiben, einen beliebigen anderen Bundler verwenden oder den unten beschriebenen Aufbau
übernehmen - Deine Wahl.

Das `default`-Theme baut seine Assets nun mal mit [Vite](https://vitejs.dev/) aus Quelldateien
in `src/scss/` und `src/js/`. Falls Du keine eigene Präferenz hast, ist das ein brauchbarer
Ausgangspunkt zum Übernehmen:

```
cd public/assets/themes/theme-name
npm install
npm run build   # einmaliger Produktions-Build nach dist/
npm run dev     # baut dist/ bei jeder Änderung neu (vite build --watch)
```

Seine `vite.config.js` bündelt `src/js/frontend.js` (inkl. allem, was diese Datei importiert,
unter anderem den SCSS-Einstiegspunkt `src/scss/default.scss`) zu `dist/theme.js` und
`dist/default.css` und lässt dabei Autoprefixer sowie cssnano über das CSS laufen. Ein kleines,
eigenes Vite-Plugin `copyAssets()` kopiert danach ein paar Dateien __unverarbeitet__ (ohne
Sass/PostCSS/Bundling) nach `dist/`:

* `src/editor.css` → `dist/editor.css`
* `src/tinyMCE_config.js` → `dist/tinyMCE_config.js`
* die Bootstrap-Icons-Webfonts → `dist/fonts/`

Wenn Du diesen Aufbau für ein neues Theme übernimmst, beachte diesen Unterschied: Alles, was in
`vite.config.js` unter `rollupOptions.input` referenziert wird, durchläuft die normale
Bundle-Pipeline - alles, was über `copyAssets()` läuft, nicht.

### Theme/Template pro Seite auswählen

Welches Theme und welches Layout-Template für eine Anfrage tatsächlich verwendet wird, wird in
`app/smarty.php` ermittelt, grob in dieser Reihenfolge:

1. Das seitenweite Standard-Theme und -Layout (`Einstellungen → System`).
2. Ist die Einstellung "Benutzer-Template" (`prefs_usertemplate`) auf `on` oder `overwrite`
   gesetzt, kann ein Theme-Switcher dies pro Session überschreiben
   (`$_SESSION['prefs_template']` / `$_SESSION['prefs_template_stylesheet']`) - gedacht für
   Theme-Entwickler, um verschiedene Themes/Stylesheets zu testen, ohne die seitenweite
   Einstellung zu ändern.
3. Hat die Seite selbst ein Theme und Layout zugewiesen (`page_template`, `page_template_layout`
   - ausgewählt über ein Dropdown in der Seiten-Editor-Seitenleiste, oder auf dem Sentinel-Wert
   `use_standard` belassen, um auf Schritt 1/2 zurückzufallen), hat das Vorrang.
   `page_template_stylesheet` wird hier ebenfalls ausgelesen, der Seiten-Editor selbst bietet
   dafür aber keine pro-Seite-Auswahl - nur die globale Themes-Verwaltungsseite lässt Dich pro
   Theme ein seitenweites Standard-Stylesheet festlegen.
4. Steht `prefs_usertemplate` auf `overwrite` und das Session-Theme (aus Schritt 2) besitzt eine
   Template-Datei mit demselben Namen wie das Layout-Template der Seite, gewinnt das
   Session-Theme.

Das Layout-Dropdown im Seiten-Editor wird gebaut, indem das `templates/`-Verzeichnis jedes
Themes nach Dateien durchsucht wird, die auf `layout*.tpl` passen (`acp/core/pages/pages-edit.php`),
gruppiert nach Theme - ein Theme kann also beliebig viele Layouts mitbringen
(`layout_default.tpl`, `layout_fullwidth.tpl`, `layout_landing.tpl`, ...), und jedes davon taucht
automatisch auf, ohne dass es irgendwo extra registriert werden müsste. Dasselbe Muster (ein Glob
pro Dateinamen-Präfix) wird für das seitenweite Standard-Layout auf der globalen
Themes-Verwaltungsseite wiederverwendet, und - mit `snippet*.tpl` statt `layout*.tpl` - auch für
die Template-Auswahl im Snippet-Editor.

Sobald `$se_template` feststeht, wird Smartys Template-Verzeichnis auf
`[themes/{$se_template}/templates/, themes/default/templates/]` gesetzt (in dieser Reihenfolge)
- jede `.tpl`-Datei, die Dein Theme nicht mitbringt, wird also automatisch aus dem `default`-Theme
geladen. Was das in der Praxis bedeutet und wo derselbe Fallback __nicht__ gilt (Deine
`dist/`-CSS/JS-Dateien), steht unter
[Vererbung vom Default-Theme](09-01-01-templates.md#vererbung-vom-default-theme).

## Zusätzliche Daten schreiben (PHP) {#zusaetzliche-daten-schreiben-php}

#### themes/theme-name/php/page-values.php

Über diese Datei wird der Seiten-Editor um einen **"Theme"-Tab** erweitert. 
Dieser erscheint, sobald eine Seite mit dem Theme `theme-name`gespeichert wurde.
Die Daten werden in der Spalte `page_template_values` als JSON gespeichert.
Ausgelesen werden die Daten in der Variable `$get_page['page_template_values']`. 

Über den Variablennamen `theme_values['..']` werden Daten übergeben und automatisch
in `page_template_values` gespeichert.

```PHP
<?php
// themes/default/php/page-values.php
global $get_page;
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$page_template_data = json_decode($get_page['page_template_values'],true);
$page_template_teaser = html_entity_decode($page_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $page_template_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

#### themes/theme-name/php/category-values.php

Analog zur Seiten-Erweiterung wird hier der **Kategorie-Editor** um einen
"Theme"-Tab erweitert.
Die Daten werden in der Spalte `cat_template_values` als JSON gespeichert.
Ausgelesen werden die Daten in der Variable `$get_category['cat_template_values']`.

Über den Variablennamen `theme_values['..']` werden Daten übergeben und automatisch
in `cat_template_values` gespeichert.

```PHP
<?php
// themes/theme-name/php/category-values.php
global $get_category;
$category_template_data = json_decode($get_category['cat_template_values'],true);
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$category_teaser = html_entity_decode($category_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $category_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

## Theme-XHR-Endpunkt {#theme-xhr-endpunkt}

`themes/theme-name/php/xhr.php` ist die Stelle, an der Dein Theme eigene AJAX-/HTMX-Anfragen
verarbeitet (z. B. ein `hx-get` in einem Deiner Templates). Anfragen an
`/xhr/themes/{theme-name}/...` werden direkt an diese Datei geroutet (siehe
`app/handlers/xhr-routes.php`) - es gibt __kein weiteres eingebautes Sub-Routing__, Deine Datei
muss den restlichen Pfad also selbst auswerten (z. B. über `$requestPathParts`), um zu
entscheiden, was zu tun ist:

```PHP
<?php
// themes/theme-name/php/xhr.php
// wird bei jeder Anfrage an /xhr/themes/theme-name/... aufgerufen
global $requestPathParts;

// Beispiel: /xhr/themes/theme-name/newsletter-signup/
if (($requestPathParts[3] ?? '') === 'newsletter-signup') {
    // Anfrage verarbeiten, z. B. $_POST auslesen, DB-Zugriff, ein Partial-.tpl ausgeben
}
```

Das `default`-Theme liefert eine leere `php/xhr.php` als Ausgangspunkt mit, falls Du eine
benötigst.

## Hooks {#hooks}

SwiftyEdit feuert eine kleine Anzahl von Frontend-Hooks rund um die Seiten-/Produktdarstellung
(siehe [Hooks](09-03-hooks.md) für den allgemeinen Hook-Mechanismus und wie Plugins Callbacks
registrieren). Die folgenden sind direkt für Deine Templates relevant - die vollständige,
maßgebliche Liste steht immer in `app/hooks/hooks-map.php`:

| Hook                      | Typ     | Context                    | Relevant für Templates, weil...                                                                    |
|---------------------------|---------|------------------------------|--------------------------------------------------------------------------------------------------------|
| `product.display.before`  | Filter  | `product_id`, `product`     | Läuft vor der Darstellung einer Produktseite; Plugins können `$product_data` verändern.               |
| `product.display.actions` | Filter  | `product_id`, `product`     | Baut das Array `$product_plugin_actions` auf, das an `products-display.tpl` übergeben wird (siehe unten). |
| `product.display.after`   | Aktion  | `product_id`, `product`     | Feuert nach der Darstellung (Tracking, Empfehlungen) - keine Template-Variablen betroffen.            |
| `page.display.after`      | Aktion  | `page_data`, `query`        | Feuert nach jeder gerenderten Seite - keine Template-Variablen betroffen.                              |

`product.display.actions` ist der Hook, den Du tatsächlich rendern musst: Jedes Plugin
(einschließlich der eingebauten Listen-Funktion) kann einen Eintrag an `$product_plugin_actions`
anhängen, und Dein `products-display.tpl` muss darüber iterieren und jeden Eintrag passend zu
seinem `type` rendern. So sieht die Implementierung im Standard-Theme aus:

```smarty
{foreach from=$product_plugin_actions item=action}
    {if $action.type == 'button'}
        <button type="submit" name="{$action.name|escape}" value="{$action.value|escape}"
                class="{$action.class|escape}">{$action.label|escape}</button>
    {elseif $action.type == 'button_htmx'}
        <button type="button" class="{$action.class|escape}"
                hx-get="{$action.hx_get|escape}&product_href={$product_href|escape:'url'}"
                hx-target="{$action.hx_target|escape}" hx-swap="{$action.hx_swap|escape}">
            {$action.label|escape}
        </button>
    {elseif $action.type == 'link'}
        <a class="{$action.class|escape}" href="{$action.href|escape}">{$action.label|escape}</a>
    {/if}
{/foreach}
```

Wenn Dein Theme `products-display.tpl` komplett ersetzt, musst Du eine vergleichbare Schleife
nachbauen - sonst tauchen von Plugins bereitgestellte Produkt-Aktionen (u. a. "Zur Liste
hinzufügen") stillschweigend nicht auf.

## UI synchron halten: eigene HX-Trigger-Events

Unabhängig von den Hooks oben antworten mehrere Frontend-XHR-Endpunkte auf eine
zustandsändernde Anfrage mit einem `HX-Trigger`-Response-Header, der ein oder mehrere eigene
Events benennt - das ist reines [HTMX](https://htmx.org/headers/hx-trigger/), kein
SwiftyEdit-eigener Mechanismus. Jedes Element auf der Seite kann darauf reagieren, indem es das
Event in sein eigenes `hx-trigger`-Attribut aufnimmt, typischerweise so:

```smarty
<span id="shopping-cart-trigger" hx-get="/xhr/se/counter/?sc_items"
      hx-trigger="load, update_user_status from:body" hx-swap="innerHTML">0</span>
```

`load` rendert es einmal beim Laden; `{event} from:body` bedeutet "führe diese Anfrage außerdem
erneut aus, sobald dieses Event auf `<body>` gefeuert wird" - `from:body` ist wichtig, weil die
Antwort, die das Event auslöst, und das Element, das darauf reagieren soll, meist zwei völlig
unabhängige Teile der Seite sind. Die aktuell verwendeten Events:

| Event                          | Ausgelöst von                                              | Verwendet für                                     |
|----------------------------------|------------------------------------------------------------|--------------------------------------------------|
| `update_user_status`             | `login.php`, `wishlist.php`, `products.php`                | Konto-/Warenkorb-Status im Header (z. B. Artikelanzahl). |
| `cart_item_added`                 | `products.php`                                             | Bump-Animation des Warenkorb-Icons - die eine Ausnahme, die nicht deklarativ per `hx-trigger`, sondern per plain JS (`document.body.addEventListener(...)` in `frontend.js`) abgehört wird, da sie eine CSS-Animation statt eines Neuladens auslöst. |
| `update_wishlists`                | `wishlist.php` (Liste anlegen/umbenennen/löschen)           | Die Listen-Auswahl/-Übersichtsspalte.              |
| `update_wishlist_detail`          | `wishlist.php` (Einträge einer Liste hinzufügen/entfernen/umsortieren) | Die Detailansicht einer einzelnen Liste.  |
| `update_comments`, `update_comment_posted` | `comments.php`                                    | Der Kommentarblock unter einer Seite/einem Beitrag. |
| `update_votings_{id}`             | `ajax.votings.php` (`{id}` = ID des bewerteten Beitrags/Events) | Die Auf-/Abstimmungs-Zähler dieses konkreten Eintrags - beim Abhören den exakten Event-Namen mit derselben ID bilden. |
| `changed_password`                | `profile.php`                                              | Der Passwort-Tab auf der Profilseite.              |
| `changed_mail_temp`               | `profile.php`                                              | Der Hinweis auf eine ausstehende E-Mail-Änderung auf der Profilseite. |
| `changed_avatar`                  | `profile.php`                                              | Die Avatar-Vorschau auf der Profilseite.           |

Wenn Dein Theme eigene zustandsändernde XHR-Aktionen ergänzt, kannst Du auf dieselbe Weise einen
`HX-Trigger`-Header feuern - so kann jeder andere Teil der Seite (auch von anderen Plugins
hinzugefügte Elemente) darauf reagieren, ohne dass Du wissen musst, wer sonst noch Bescheid
wissen muss.

## Custom Smarty-Modifier

`app/smarty.php` registriert ein paar native PHP-Funktionen zusätzlich zu den von Smarty
mitgelieferten Modifiern: `|htmlentities`, `|strtolower` und `|trim`. Besonders `trim` ist
relevant - Smartys 5 `DefaultExtension` enthält von Haus aus keinen `trim`-Modifier mehr, ohne
diese manuelle Registrierung würde `{$var|trim}` in Deinen Templates also fehlschlagen.

## Besonderheiten

### tinyMCE {#tinymce}
Ein Template ist nicht nur für das Aussehen Deiner Website verantwortlich,
sondern kann auch die Optik bzw. die Funktionen des Editors tinyMCE steuern.
Damit kannst Du erreichen, dass sich die WYSIWYG Ansicht so nah als möglich am Original-Layout
(also dem Frontend) orientiert.

__Zwei Dateien sind dafür maßgeblich verantwortlich:__

* themes/{theme}/dist/editor.css
* themes/{theme}/dist/tinyMCE_config.js

Die CSS Datei ist für das Aussehen der Inhalte im Editor verantwortlich.
Dies ist der einfachste Weg, den Editor an Dein Layout anzupassen.
Die JavaScript Datei ist für die Konfiguration zuständig.
Weitere Informationen findest Du in der tinyMCE Dokumentation.

Weitere Informationen zur Konfiguration findest Du in der
[tinyMCE Dokumentation](https://www.tiny.cloud/docs/tinymce/latest/)

### ACE-Editor

SwiftyEdit bringt außerdem den ACE-Editor (`public/assets/editors/ace/`) als Alternative zu
tinyMCE mit, mit einem eigenen, festen Satz an Syntax-Themes (`theme-chrome.js`,
`theme-twilight.js`). Anders als bei tinyMCE gibt es aktuell keinen theme-spezifischen
Anpassungspunkt (kein `ace_config.js` oder vergleichbares CSS in `dist/`) - das Aussehen von ACE
wird von Deinem Theme nicht beeinflusst.
