# Das Templatesystem
Als Templatesystem kommt smarty zum Einsatz.
Wer ein eigenes Template erstellen möchte, sollte sich also zunächst mit der smarty Dokumentation
vertraut machen.

## Gut zu wissen

* Alle Themes befinden sich im Verzeichnis `/public/assets/themes/`.
* Die Themes `administration` und `default` werden bei jedem Update überschrieben.
* Themes können den Funktionsumfang von SwiftyEdit erweitern

## Verzeichnisstruktur

* themes/theme-name/
    * dist/ (__erforderlich__: SwiftyEdits Templates verlinken diese Dateien direkt namentlich,
      siehe [Theme-Assets bauen](#theme-assets-bauen) dazu, wie sie dort hineinkommen)
        * core.css, core.js (werden immer geladen)
        * shop.css, shop.js, events.css, comments.css, posts.css (optionale Komponenten, siehe
          [Optionale Theme-Komponenten](#optionale-theme-komponenten) - werden nur bei Auswahl geladen)
        * editor.css, tinyMCE_config.js (siehe [tinyMCE](#tinymce))
        * fonts/ (nur falls Dein CSS sie braucht, z. B. die Bootstrap-Icons-Webfonts des
          Standard-Themes)
    * src/ (optional - nur vorhanden, wenn Du Deine Assets aus Quelldateien baust; das
      `default`-Theme macht das mit Vite, siehe [Theme-Assets bauen](#theme-assets-bauen))
        * scss/ (Core-Einstiegspunkt `core.scss`, gespiegelt zum `js/`-Layout unten:
          `scss/components/` enthält je einen Einstiegspunkt pro optionaler Komponente, z. B.
          `scss/components/shop.scss`; `scss/lib/` enthält Sass-Partials, die von mehr als einem
          Einstiegspunkt importiert werden, z. B. `scss/lib/_variables.scss`. Die eigenen Styles
          einer Komponente stehen direkt in ihrem `scss/components/*.scss`-Einstiegspunkt - keine
          separate Partial-Datei pro Komponente, die synchron zu halten wäre, da sie sonst
          niemand importiert)
        * js/ (Core-JS-Einstiegspunkt `frontend.js`; `js/components/` enthält je eine Datei pro
          optionaler Komponente, automatisch erkannt von `vite.config.js`, z. B.
          `js/components/shop.js`; `js/lib/` enthält Hilfsmodule, die von Einstiegspunkten
          importiert werden, selbst aber keine Komponenten sind, z. B. `js/lib/wishlist.js`)
        * editor.css, tinyMCE_config.js (siehe [tinyMCE](#tinymce))
    * images/ (Vorschaubild, Icon usw. - werden in der Theme-Auswahl angezeigt)
    * docs/ (optional, Deine eigene Theme-Dokumentation)
    * lang/ (optional, z. B. `de.json`, `en.json` - siehe
      [Die ACP-Oberfläche Deines Themes übersetzen](#die-acp-oberflaeche-deines-themes-uebersetzen))
    * php/
        * index.php (allgemeine Theme-Funktionen, nur Frontend)
        * options.php (optional) verwaltet Theme-Optionen (Frontend und Backend)
        * xhr.php (optional) XHR-Routing-Datei (Frontend), siehe [Theme-XHR-Endpunkt](#theme-xhr-endpunkt)
        * page-values.php / category-values.php (optional), siehe [Zusätzliche Daten schreiben](#zusaetzliche-daten-schreiben-php)
    * templates/ (Deine Smarty-Template-Dateien, siehe [Templates](09-01-01-templates.md))
    * templates-mail/ (Deine Mail-Templates, siehe [Mail-Templates](09-01-01-templates.md#mail-templates))
    * package.json, vite.config.js (optional - nur falls Du wie das `default`-Theme mit Vite
      baust, siehe [Theme-Assets bauen](#theme-assets-bauen))
    * info.json (Theme-Manifest: Name, Version, Autor, Beschreibung - siehe
      [Die info.json-Datei](#die-infojson-datei))
    * poster.png / images/icon.png (optional, Theme-Vorschaubild in der Theme-Auswahl)
    * readme.md (optional, wird im ACP-Theme-Editor und Doku-Browser geparst angezeigt)

## Die info.json-Datei {#die-infojson-datei}

Jedes Theme sollte eine `info.json`-Datei in seinem Wurzelverzeichnis mitbringen. Sie folgt
demselben Aufbau wie die [info.json eines Plugins](09-02-plugins.md#die-infojson-datei), nur
dass `addon.type` auf `theme` statt `plugin` gesetzt wird und kein `navigation`-Block nötig
ist (die eigene Backend-Oberfläche eines Themes ist seine `php/options.php`-Datei, erreichbar
über den festen "Optionen"-Link auf der Themes-Verwaltungsseite - keine Liste von
Navigationseinträgen).

```json
{
  "addon": {
    "id": "my-theme",
    "type": "theme",
    "name": "My Theme",
    "version": "1.0",
    "build": 1,
    "author": "Your Name",
    "description": "Eine kurze Beschreibung Deines Themes",
    "update_url": "https://your-server.com/themes/my-theme/info.json"
  },
  "versions": [
    {
      "version": "1.0",
      "build": 1,
      "requires_build": "26-0183",
      "download_url": "https://your-server.com/themes/my-theme/my-theme-1.zip"
    }
  ]
}
```

Wie bei Plugins sind nur `name`, `version`, `author` und `description` erforderlich, wenn Dein
Theme ausschließlich manuell installiert wird. Die übrigen Felder (`id`, `type`, `build`,
`versions[]`, `update_url`, `requires_build`) werden nur gebraucht, wenn Dein Theme über den
"Von URL installieren"-/Katalog-Ablauf des ACP installier- und aktualisierbar sein soll (die
vollständige Feldreferenz, erlaubten ZIP-Dateitypen und das Update-Check-Verhalten stehen unter
[Plugins → Die info.json Datei](09-02-plugins.md#die-infojson-datei) - sie gelten für Themes
unverändert).

> **Veraltet: `info.xml`:** Themes von vor diesem Format bringen unter Umständen noch das
> ältere `info.xml`-Manifest mit (Name, Version, Lizenz, Autor, benötigte Core-Version) statt
> einer `info.json`. SwiftyEdit liest es als Fallback, wenn keine `info.json` vorhanden ist -
> so ein Theme taucht im ACP also weiterhin korrekt auf. `info.xml` kennt aber kein Äquivalent
> zu `id`/`build`/`versions[]`/`update_url`, ein so erkanntes Theme kann daher nie über eine URL
> installiert oder aktualisiert werden. Neue Themes sollten stattdessen eine `info.json`
> mitbringen - `info.xml` wird außer für diesen Fallback nirgends mehr gelesen.

## Theme-Assets bauen {#theme-assets-bauen}

SwiftyEdit ist es egal, wie die Dateien in `dist/` entstanden sind - wichtig ist nur, dass sie
unter den erwarteten Namen existieren. `head.tpl` verlinkt `dist/core.css` und
`dist/core.js` direkt (und `maintenance.tpl` macht dasselbe für `default`), und die
tinyMCE-Integration erwartet `dist/editor.css` und `dist/tinyMCE_config.js` (siehe
[tinyMCE](#tinymce)). Über diesen Datei-/Verzeichnis-Vertrag hinaus ist der Einsatz eines
Build-Tools komplett optional: Du kannst reines CSS und JS von Hand direkt nach `dist/`
schreiben, einen beliebigen anderen Bundler verwenden oder den unten beschriebenen Aufbau
übernehmen - Deine Wahl.

Das `default`-Theme baut seine Assets nun mal mit [Vite](https://vitejs.dev/) aus Quelldateien
in `src/scss/` und `src/js/`. Falls Du keine eigene Präferenz hast, ist das ein brauchbarer
Ausgangspunkt zum Übernehmen:

```
cd public/assets/themes/theme-name
npm install
npm run build   # einmaliger Produktions-Build nach dist/
npm run dev     # baut dist/ bei jeder Änderung neu (vite build --watch)
```

Seine `vite.config.js` deklariert einen festen `rollupOptions.input`-Eintrag, `core` (aus
`src/js/frontend.js`, importiert den Einstiegspunkt `core.scss`), plus einen Eintrag pro Datei,
die sie in `src/js/components/` findet - ein kleiner Helfer `discoverComponentEntries()` macht
dafür ein `fs.readdirSync()` über diesen Ordner, sodass eine neue
[optionale Komponente](#optionale-theme-komponenten) einfach "Datei hinzufügen" bedeutet, ohne
`vite.config.js` anzufassen. Jeder Komponenten-Entry importiert seinen eigenen SCSS-Einstiegspunkt
(z. B. `src/scss/components/shop.scss`, der die tatsächlichen Style-Regeln dieser Komponente
direkt enthält - keine separate Partial-Datei pro Komponente, da sie sonst niemand importieren
würde) und, falls relevant, eigenes JS. Hilfsmodule, die ein Entry importiert, die aber selbst
keine Komponenten sind (`theme_switch.js`, `wishlist.js`), liegen stattdessen in `src/js/lib/` -
alles direkt unter `src/js/components/` wird zu einer eigenen Komponente, ein versehentlich dort
abgelegtes Hilfsmodul würde also fälschlich mit auftauchen. Vite benennt die Ausgabedatei jedes
Eintrags nach seinem Input-Key (`core.css`/`core.js`, `shop.css`/`shop.js`, ...) und lässt
Autoprefixer sowie cssnano über das gesamte CSS laufen. Die SCSS-Einstiegspunkte der Komponenten
binden nur Bootstraps Functions/Variables/Maps ein (`src/scss/lib/_bootstrap-vars.scss`), nicht
das komplette kompilierte Bootstrap-CSS - das steckt bereits einmal in `core.css`. Falls Du eine
weitere Komponente ergänzt, beachte das: Ein Import des vollständigen `bootstrap`-Partials aus einem
Komponenten-Entry würde das gesamte Bootstrap-CSS zusätzlich in dieses Komponenten-Bundle
duplizieren. Ein kleines, eigenes Vite-Plugin `copyAssets()` kopiert danach ein paar Dateien
__unverarbeitet__ (ohne Sass/PostCSS/Bundling) nach `dist/`:

* `src/editor.css` → `dist/editor.css`
* `src/tinyMCE_config.js` → `dist/tinyMCE_config.js`
* die Bootstrap-Icons-Webfonts → `dist/fonts/`

Wenn Du diesen Aufbau für ein neues Theme übernimmst, beachte diesen Unterschied: Alles, was in
`vite.config.js` unter `rollupOptions.input` referenziert wird, durchläuft die normale
Bundle-Pipeline - alles, was über `copyAssets()` läuft, nicht.

### Optionale Theme-Komponenten {#optionale-theme-komponenten}

Das `default`-Theme trennt sein Shop-/Events-/Kommentar-/Beitrags-Styling (und beim Shop
zusätzlich das JS - Wunschlisten-Sortierung, Mengen-Stepper, Preis-Regler) aus dem immer
geladenen Core-Bundle heraus in eigene Dateien `dist/shop.{css,js}`, `dist/events.css`,
`dist/comments.css` und `dist/posts.css` - eine Seite, die einen dieser Bereiche gar nicht
nutzt, lädt dessen CSS/JS also erst gar nicht. Alles Globale (jQuery, Bootstraps JS, htmx,
GLightbox, der Dark-Mode-Umschalter, Header/Footer der Seite) bleibt in `core.css`/`core.js`
und wird immer geladen.

Welche Komponenten überhaupt existieren, ist nirgends in PHP oder Smarty hartkodiert - das
ergibt sich rein aus einer Namenskonvention auf `dist/`, in `php/theme-components.php`:

> Jede Datei `dist/<id>.css` und/oder `dist/<id>.js` ist eine auswählbare Komponente namens
> `<id>` (eine Komponente braucht nicht beide Dateien - nur CSS oder nur JS ist in Ordnung),
> außer einer kurzen reservierten Liste (`core`, `editor`, `tinyMCE_config`), die keine
> optionalen Komponenten sind.

`se_theme_component_ids($theme_dist_dir)` liefert die so gefundene, sortierte Liste der IDs, und
`se_theme_component_has_css()`/`se_theme_component_has_js()` prüfen, welche der beiden Dateien
eine gegebene ID tatsächlich hat (eine leere Platzhalterdatei, wie sie die CSS-only-Komponenten
des `default`-Themes als ihren `.js`-Entry mitbringen, zählt nicht - siehe
[Theme-Assets bauen](#theme-assets-bauen) dazu, warum es die überhaupt gibt). Weil die Erkennung
`dist/` liest statt `src/`, funktioniert sie unabhängig davon, ob (oder wie) ein Theme mit Vite
gebaut wird - eine von Hand geschriebene `dist/newsletter.css` ganz ohne Build-Schritt dahinter
wird genauso erkannt. Das heißt auch: eine neue Komponente zum `default`-Theme hinzuzufügen ist
wirklich nur "Datei rein, neu bauen" - keine Änderung an `page-values.php`, `options.php` oder
`head.tpl` nötig, nur optional ein Schlüssel `label_component_<id>` in `lang/*.json` für eine
schönere Beschriftung im Picker - siehe
[Die ACP-Oberfläche Deines Themes übersetzen](#die-acp-oberflaeche-deines-themes-uebersetzen).
Ohne einen solchen Schlüssel fällt der Picker auf die rohe, großgeschriebene ID zurück.

Welche Komponenten für eine bestimmte Seite geladen werden, ist eine Pro-Seite-Entscheidung, die
im "Theme"-Tab des Seiteneditors getroffen wird (`php/page-values.php`, das `theme-components.php`
für die Checkbox-Liste nutzt - siehe
[Zusätzliche Daten schreiben](#zusaetzliche-daten-schreiben-php)) und zusammen mit dem
Teaser-Text in `page_template_values` gespeichert wird, unter den Schlüsseln `components_mode`
(`"all"` oder `"custom"`) sowie `comp_<id>` (`"1"` wenn aktiviert, eine pro gefundener ID).
Seiten, die vor Einführung dieser Option gespeichert wurden, haben noch keinen
`components_mode`-Schlüssel - das wird wie `"all"` behandelt, sodass bestehende Seiten weiterhin
alles laden, genau wie beim alten Einzel-Bundle-Build.

Damit diese Pro-Seite-Entscheidung im Frontend zur Verfügung steht, dekodiert
`app/template-setup.php` `page_template_values` in ein `$theme_values`-Array, bevor die
`php/options.php` Deines Themes läuft - jedes Theme kann in seiner `options.php` mit
`$theme_values['dein_schluessel']` auf alles zugreifen, was `page-values.php` dort abgelegt hat,
nicht nur für das Laden von Komponenten. Die `options.php` des `default`-Themes führt dieselbe
`theme-components.php`-Erkennung erneut aus und wandelt sie in ein an Smarty zugewiesenes,
nach ID gruppiertes Array `$se_theme_components` um
(`['shop' => ['enabled' => bool, 'has_css' => bool, 'has_js' => bool], ...]`), das `head.tpl`
dann durchläuft, um zu entscheiden, welche `<link>`-/`<script>`-Tags ausgegeben werden - auch im
Template taucht kein Komponentenname namentlich auf:

```smarty
{foreach $se_theme_components as $component_id => $component}
    {if $component.enabled && $component.has_css}
        <link rel="stylesheet" media="screen" href="{$se_inc_dir}/themes/{$se_template}/dist/{$component_id}.css" />
    {/if}
{/foreach}
```

Wenn Du ein eigenes Theme mit mehreren optionalen Funktionsbereichen baust, ist dieses ganze
Muster brauchbar zum Übernehmen: `theme-components.php` neben Deine eigene `page-values.php` und
`options.php` legen, `src/js/components/` (falls Du Vite nutzt) oder Deinen eigenen Build-Schritt
entscheiden lassen, was in `dist/` landet, und in Deinen Templates über `$se_theme_components`
iterieren statt Komponenten irgendwo namentlich zu nennen.

### Theme/Template pro Seite auswählen

Welches Theme und welches Layout-Template für eine Anfrage tatsächlich verwendet wird, wird in
`app/smarty.php` ermittelt, grob in dieser Reihenfolge:

1. Das seitenweite Standard-Theme und -Layout (`Einstellungen → System`).
2. Ist die Einstellung "Benutzer-Template" (`prefs_usertemplate`) auf `on` oder `overwrite`
   gesetzt, kann ein Theme-Switcher dies pro Session überschreiben
   (`$_SESSION['prefs_template']` / `$_SESSION['prefs_template_stylesheet']`) - gedacht für
   Theme-Entwickler, um verschiedene Themes/Stylesheets zu testen, ohne die seitenweite
   Einstellung zu ändern.
3. Hat die Seite selbst ein Theme und Layout zugewiesen (`page_template`, `page_template_layout`
   - ausgewählt über ein Dropdown in der Seiten-Editor-Seitenleiste, oder auf dem Sentinel-Wert
   `use_standard` belassen, um auf Schritt 1/2 zurückzufallen), hat das Vorrang.
   `page_template_stylesheet` wird hier ebenfalls ausgelesen, der Seiten-Editor selbst bietet
   dafür aber keine pro-Seite-Auswahl - nur die globale Themes-Verwaltungsseite lässt Dich pro
   Theme ein seitenweites Standard-Stylesheet festlegen.
4. Steht `prefs_usertemplate` auf `overwrite` und das Session-Theme (aus Schritt 2) besitzt eine
   Template-Datei mit demselben Namen wie das Layout-Template der Seite, gewinnt das
   Session-Theme.

Das Layout-Dropdown im Seiten-Editor wird gebaut, indem das `templates/`-Verzeichnis jedes
Themes nach Dateien durchsucht wird, die auf `layout*.tpl` passen (`acp/core/pages/pages-edit.php`),
gruppiert nach Theme - ein Theme kann also beliebig viele Layouts mitbringen
(`layout_default.tpl`, `layout_fullwidth.tpl`, `layout_landing.tpl`, ...), und jedes davon taucht
automatisch auf, ohne dass es irgendwo extra registriert werden müsste. Dasselbe Muster (ein Glob
pro Dateinamen-Präfix) wird für das seitenweite Standard-Layout auf der globalen
Themes-Verwaltungsseite wiederverwendet, und - mit `snippet*.tpl` statt `layout*.tpl` - auch für
die Template-Auswahl im Snippet-Editor.

Sobald `$se_template` feststeht, wird Smartys Template-Verzeichnis auf
`[themes/{$se_template}/templates/, themes/default/templates/]` gesetzt (in dieser Reihenfolge)
- jede `.tpl`-Datei, die Dein Theme nicht mitbringt, wird also automatisch aus dem `default`-Theme
geladen. Was das in der Praxis bedeutet und wo derselbe Fallback __nicht__ gilt (Deine
`dist/`-CSS/JS-Dateien), steht unter
[Vererbung vom Default-Theme](09-01-01-templates.md#vererbung-vom-default-theme).

## Die ACP-Oberfläche Deines Themes übersetzen {#die-acp-oberflaeche-deines-themes-uebersetzen}

Strings, die Dein Theme im __ACP__ ausgibt (die Felder seiner `php/options.php` auf der
"Optionen"-Seite des Themes, oder ein Tab wie `page-values.php`/`category-values.php` unten),
kannst Du genauso übersetzen wie Plugins das tun: eine flache Schlüssel/Wert-JSON-Datei pro
Sprache in `lang/` (`lang/de.json`, `lang/en.json`, ...). Geladen wird sie mit
`se_return_addon_translations($theme_id, 'theme')` (dieselbe Funktion, die Plugins über
`se_return_addon_translations($plugin_id)` nutzen - Themes übergeben nur zusätzlich `'theme'`
als zweites Argument, damit unter `SE_THEMES` statt `SE_PLUGINS` gesucht wird). Sie liest die
Datei zur aktuellen Sprache der Admin-Session und fällt auf `lang/en.json` zurück, falls diese
nicht existiert - Dein Theme muss also nicht jede Sprache abdecken, die SwiftyEdit mitbringt,
sondern nur die, die Du unterstützen willst:

```PHP
<?php
// themes/theme-name/php/page-values.php
$theme_lang = se_return_addon_translations('theme-name', 'theme');
echo '<h5>'.$theme_lang['title_theme_values'].'</h5>';
```

```json
// themes/theme-name/lang/en.json
{
  "title_theme_values": "Theme Values"
}
```

Diese Funktion ist nur im ACP definiert (`acp/core/functions_addons.php`, bei jeder
Admin-Anfrage automatisch geladen) - im Frontend existiert sie nicht, ruf sie also nicht aus
`templates/*.tpl` oder dem Frontend-PHP Deines Themes auf. Frontend-Strings laufen stattdessen
über das reguläre `$lang`-Array bzw. das Sprachpaket (siehe die Sprachpaket-Dateien unter
`languages/`).

## Zusätzliche Daten schreiben (PHP) {#zusaetzliche-daten-schreiben-php}

#### themes/theme-name/php/page-values.php

Über diese Datei wird der Seiten-Editor um einen **"Theme"-Tab** erweitert. 
Dieser erscheint, sobald eine Seite mit dem Theme `theme-name`gespeichert wurde.
Die Daten werden in der Spalte `page_template_values` als JSON gespeichert.
Ausgelesen werden die Daten in der Variable `$get_page['page_template_values']`. 

Über den Variablennamen `theme_values['..']` werden Daten übergeben und automatisch
in `page_template_values` gespeichert.

```PHP
<?php
// themes/default/php/page-values.php
global $get_page;
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$page_template_data = json_decode($get_page['page_template_values'],true);
$page_template_teaser = html_entity_decode($page_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $page_template_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

#### themes/theme-name/php/category-values.php

Analog zur Seiten-Erweiterung wird hier der **Kategorie-Editor** um einen
"Theme"-Tab erweitert.
Die Daten werden in der Spalte `cat_template_values` als JSON gespeichert.
Ausgelesen werden die Daten in der Variable `$get_category['cat_template_values']`.

Über den Variablennamen `theme_values['..']` werden Daten übergeben und automatisch
in `cat_template_values` gespeichert.

```PHP
<?php
// themes/theme-name/php/category-values.php
global $get_category;
$category_template_data = json_decode($get_category['cat_template_values'],true);
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$category_teaser = html_entity_decode($category_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $category_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

## Theme-XHR-Endpunkt {#theme-xhr-endpunkt}

`themes/theme-name/php/xhr.php` ist die Stelle, an der Dein Theme eigene AJAX-/HTMX-Anfragen
verarbeitet (z. B. ein `hx-get` in einem Deiner Templates). Anfragen an
`/xhr/themes/{theme-name}/...` werden direkt an diese Datei geroutet (siehe
`app/handlers/xhr-routes.php`) - es gibt __kein weiteres eingebautes Sub-Routing__, Deine Datei
muss den restlichen Pfad also selbst auswerten (z. B. über `$requestPathParts`), um zu
entscheiden, was zu tun ist:

```PHP
<?php
// themes/theme-name/php/xhr.php
// wird bei jeder Anfrage an /xhr/themes/theme-name/... aufgerufen
global $requestPathParts;

// Beispiel: /xhr/themes/theme-name/newsletter-signup/
if (($requestPathParts[3] ?? '') === 'newsletter-signup') {
    // Anfrage verarbeiten, z. B. $_POST auslesen, DB-Zugriff, ein Partial-.tpl ausgeben
}
```

Das `default`-Theme liefert eine leere `php/xhr.php` als Ausgangspunkt mit, falls Du eine
benötigst.

## Hooks {#hooks}

SwiftyEdit feuert eine kleine Anzahl von Frontend-Hooks rund um die Seiten-/Produktdarstellung
(siehe [Hooks](09-03-hooks.md) für den allgemeinen Hook-Mechanismus und wie Plugins Callbacks
registrieren). Die folgenden sind direkt für Deine Templates relevant - die vollständige,
maßgebliche Liste steht immer in `app/hooks/hooks-map.php`:

| Hook                      | Typ     | Context                    | Relevant für Templates, weil...                                                                    |
|---------------------------|---------|------------------------------|--------------------------------------------------------------------------------------------------------|
| `product.display.before`  | Filter  | `product_id`, `product`     | Läuft vor der Darstellung einer Produktseite; Plugins können `$product_data` verändern.               |
| `product.display.actions` | Filter  | `product_id`, `product`     | Baut das Array `$product_plugin_actions` auf, das an `products-display.tpl` übergeben wird (siehe unten). |
| `product.display.after`   | Aktion  | `product_id`, `product`     | Feuert nach der Darstellung (Tracking, Empfehlungen) - keine Template-Variablen betroffen.            |
| `page.display.after`      | Aktion  | `page_data`, `query`        | Feuert nach jeder gerenderten Seite - keine Template-Variablen betroffen.                              |
| `image.variants`          | Filter  | `src`, `widths`, `ratio`, `fit` | Lässt ein Plugin responsive `src`/`srcset`-Varianten für das `{img}`-Tag liefern (siehe [unten](#responsive-bilder-mit-img)) - ohne aktives Plugin rendert `{img}` weiterhin ein schlichtes `<img src>`. |

`product.display.actions` ist der Hook, den Du tatsächlich rendern musst: Jedes Plugin kann einen
Eintrag an `$product_plugin_actions` anhängen, und Dein `products-display.tpl` muss darüber
iterieren und jeden Eintrag passend zu seinem `type` rendern. Der eingebaute "Zur Liste
hinzufügen"-Button der Wunschliste läuft *nicht* über diesen Filter - er ist eine Kernfunktion und
wird über eigene, dedizierte Template-Variablen gerendert (`$show_wishlist_button`,
`$wishlist_logged_in`, `$wishlist_already_saved`, `$wishlist_login_uri`, zugewiesen in
`app/handlers/products-display.php`), damit er direkt neben dem "In den Warenkorb"-Button stehen
kann, statt dort zu landen, wo Plugin-Aktionen zufällig gerendert werden. So sieht die
Implementierung der Plugin-Aktionen-Schleife im Standard-Theme aus:

```smarty
{foreach from=$product_plugin_actions item=action}
    {if $action.type == 'button'}
        <button type="submit" name="{$action.name|escape}" value="{$action.value|escape}"
                class="{$action.class|escape}">{$action.label|escape}</button>
    {elseif $action.type == 'link'}
        <a class="{$action.class|escape}" href="{$action.href|escape}">{$action.label|escape}</a>
    {/if}
{/foreach}
```

Wenn Dein Theme `products-display.tpl` komplett ersetzt, musst Du eine vergleichbare Schleife
nachbauen - sonst tauchen von Plugins bereitgestellte Produkt-Aktionen stillschweigend nicht auf.

## UI synchron halten: eigene HX-Trigger-Events

Unabhängig von den Hooks oben antworten mehrere Frontend-XHR-Endpunkte auf eine
zustandsändernde Anfrage mit einem `HX-Trigger`-Response-Header, der ein oder mehrere eigene
Events benennt - das ist reines [HTMX](https://htmx.org/headers/hx-trigger/), kein
SwiftyEdit-eigener Mechanismus. Jedes Element auf der Seite kann darauf reagieren, indem es das
Event in sein eigenes `hx-trigger`-Attribut aufnimmt, typischerweise so:

```smarty
<span id="shopping-cart-trigger" hx-get="/xhr/se/counter/?sc_items"
      hx-trigger="load, update_user_status from:body" hx-swap="innerHTML">0</span>
```

`load` rendert es einmal beim Laden; `{event} from:body` bedeutet "führe diese Anfrage außerdem
erneut aus, sobald dieses Event auf `<body>` gefeuert wird" - `from:body` ist wichtig, weil die
Antwort, die das Event auslöst, und das Element, das darauf reagieren soll, meist zwei völlig
unabhängige Teile der Seite sind. Die aktuell verwendeten Events:

| Event                          | Ausgelöst von                                              | Verwendet für                                     |
|----------------------------------|------------------------------------------------------------|--------------------------------------------------|
| `update_user_status`             | `login.php`, `wishlist.php`, `products.php`                | Konto-/Warenkorb-Status im Header (z. B. Artikelanzahl). |
| `cart_item_added`                 | `products.php`                                             | Bump-Animation des Warenkorb-Icons - die eine Ausnahme, die nicht deklarativ per `hx-trigger`, sondern per plain JS (`document.body.addEventListener(...)` in `frontend.js`) abgehört wird, da sie eine CSS-Animation statt eines Neuladens auslöst. |
| `update_wishlists`                | `wishlist.php` (Liste anlegen/umbenennen/löschen)           | Die Listen-Auswahl/-Übersichtsspalte.              |
| `update_wishlist_detail`          | `wishlist.php` (Einträge einer Liste hinzufügen/entfernen/umsortieren) | Die Detailansicht einer einzelnen Liste.  |
| `update_comments`, `update_comment_posted` | `comments.php`                                    | Der Kommentarblock unter einer Seite/einem Beitrag. |
| `update_votings_{id}`             | `ajax.votings.php` (`{id}` = ID des bewerteten Beitrags/Events/Produkts) | Die Auf-/Abstimmungs-Zähler dieses konkreten Eintrags - beim Abhören den exakten Event-Namen mit derselben ID bilden. |
| `update_guestlist_{id}`           | `ajax.guestlist.php` (`{id}` = ID des Events)               | Der Zähler bestätigter Zusagen auf der Event-Detailseite - nur relevant, wenn die Anzahl öffentlich angezeigt wird. |
| `changed_password`                | `profile.php`                                              | Der Passwort-Tab auf der Profilseite.              |
| `changed_mail_temp`               | `profile.php`                                              | Der Hinweis auf eine ausstehende E-Mail-Änderung auf der Profilseite. |
| `changed_avatar`                  | `profile.php`                                              | Die Avatar-Vorschau auf der Profilseite.           |

Wenn Dein Theme eigene zustandsändernde XHR-Aktionen ergänzt, kannst Du auf dieselbe Weise einen
`HX-Trigger`-Header feuern - so kann jeder andere Teil der Seite (auch von anderen Plugins
hinzugefügte Elemente) darauf reagieren, ohne dass Du wissen musst, wer sonst noch Bescheid
wissen muss.

## Custom Smarty-Modifier

`app/smarty.php` registriert ein paar native PHP-Funktionen zusätzlich zu den von Smarty
mitgelieferten Modifiern: `|htmlentities`, `|strtolower` und `|trim`. Besonders `trim` ist
relevant - Smartys 5 `DefaultExtension` enthält von Haus aus keinen `trim`-Modifier mehr, ohne
diese manuelle Registrierung würde `{$var|trim}` in Deinen Templates also fehlschlagen.

## Responsive Bilder mit {img} {#responsive-bilder-mit-img}

`app/smarty.php` registriert außerdem `{img}` als Smarty-Function (`app/functions/functions.img.php`).
Es rendert immer *etwas*: ein schlichtes `<img src="...">`, wenn kein Bild-Plugin aktiv ist, oder
ein `<img srcset="..." sizes="...">` mit responsiven Breiten-Varianten, wenn eins aktiv ist (z. B.
das mitgelieferte `image-resizer`-Plugin). Dein Theme muss nie wissen, welcher Fall gerade zutrifft
- setze `{img}` schon heute ein und bekommst responsive/optimierte Bilder geschenkt, sobald ein
Plugin aktiv ist, ganz ohne Template-Änderung:

```smarty
{img src="{$product.image}" widths="400,800,1200" ratio="4:3" fit="cover"
     sizes="(max-width: 600px) 100vw, 800px" alt="{$product.title|escape}" loading="lazy"}
```

| Attribut  | Pflicht | Bedeutung |
|-----------|---------|-----------|
| `src`     | ja      | Bildpfad, z. B. `/images/foo.jpg` (der bestehende öffentliche Upload-Pfad). |
| `widths`  | nein    | Kommagetrennte Ziel-Breiten in px, je ein `srcset`-Eintrag. Ohne diesen Wert rendert `{img}` ein schlichtes `<img src>`, selbst bei aktivem Plugin - es werden keine Varianten erzeugt, die niemand angefordert hat. |
| `ratio`   | nein    | Ziel-Seitenverhältnis, z. B. `4:3`. |
| `fit`     | nein    | `cover` (Crop-Fill, Standard) oder `contain` (ganzes Bild sichtbar, kein Zuschnitt). |
| `sizes`   | nein    | Wird unverändert ins `sizes`-Attribut übernommen - eine reine Layout-Entscheidung, die weder `{img}` noch ein Plugin berechnet. |
| `alt`, `class`, `id`, `loading`, `title` | nein | Werden unverändert ins gerenderte `<img>`-Tag übernommen. |
| `width`, `height` | nein | Werden unverändert übernommen, wenn Du beide angibst. Gibst Du keins von beiden an, ermittelt `{img}` sie selbst - aus `ratio` (wenn ein Zuschnitt angefordert wurde) oder aus den echten Maßen der Originaldatei (wenn nicht). Nie geraten, das deklarierte Seitenverhältnis passt also immer zu dem, was tatsächlich ausgeliefert wird. Das reserviert den richtigen Platz im Layout, bevor das Bild lädt (verhindert Layout-Sprünge/CLS), ohne das Risiko eines falschen Verhältnisses, das das Bild sichtbar verzerren würde. |

Diesen Attribut-Vertrag und den Fallback auf ein schlichtes `<img>` legt Core fest, nicht ein
Plugin - der Vertrag bleibt also stabil, selbst wenn Du später das aktive Bild-Plugin wechselst.
Was ein Plugin tun kann: sich in den Filter `image.variants` einklinken (siehe Hook-Tabelle oben)
und daraus ein echtes `src`/`srcset` bauen; die Format-Aushandlung (AVIF/WebP/JPEG) passiert dabei
pro Anfrage über den `Accept`-Header, nicht über ein `<picture>`-Element.

## Besonderheiten

### tinyMCE {#tinymce}
Ein Template ist nicht nur für das Aussehen Deiner Website verantwortlich,
sondern kann auch die Optik bzw. die Funktionen des Editors tinyMCE steuern.
Damit kannst Du erreichen, dass sich die WYSIWYG Ansicht so nah als möglich am Original-Layout
(also dem Frontend) orientiert.

__Zwei Dateien sind dafür maßgeblich verantwortlich:__

* themes/{theme}/dist/editor.css
* themes/{theme}/dist/tinyMCE_config.js

Die CSS Datei ist für das Aussehen der Inhalte im Editor verantwortlich.
Dies ist der einfachste Weg, den Editor an Dein Layout anzupassen.
Die JavaScript Datei ist für die Konfiguration zuständig.
Weitere Informationen findest Du in der tinyMCE Dokumentation.

Weitere Informationen zur Konfiguration findest Du in der
[tinyMCE Dokumentation](https://www.tiny.cloud/docs/tinymce/latest/)

### ACE-Editor

SwiftyEdit bringt außerdem den ACE-Editor (`public/assets/editors/ace/`) als Alternative zu
tinyMCE mit, mit einem eigenen, festen Satz an Syntax-Themes (`theme-chrome.js`,
`theme-twilight.js`). Anders als bei tinyMCE gibt es aktuell keinen theme-spezifischen
Anpassungspunkt (kein `ace_config.js` oder vergleichbares CSS in `dist/`) - das Aussehen von ACE
wird von Deinem Theme nicht beeinflusst.
