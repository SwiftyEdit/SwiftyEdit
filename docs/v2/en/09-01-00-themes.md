# The template system
We use Smarty template system.
If you want to create your own template, you should be familiar with the smarty documentation.

## Good to know

* All themes are located in the `/public/assets/themes/` directory.
* The `administration` and `default` themes are overwritten on every update.
* Themes can extend the functionality of SwiftyEdit.

## Directory structure

* themes/theme-name/
    * dist/ (__required__: SwiftyEdit's templates link these files directly by name, see
      [Building the theme assets](#building-the-theme-assets) for how they get there)
        * default.css, theme.js
        * editor.css, tinyMCE_config.js (see [tinyMCE](#tinymce))
        * fonts/ (only if your CSS needs them, e.g. the default theme's bootstrap-icons webfonts)
    * src/ (optional - only present if you build your assets from source; the `default` theme
      does this with Vite, see [Building the theme assets](#building-the-theme-assets))
        * scss/ (Sass partials, entry point `default.scss`)
        * js/ (JS entry point `frontend.js` and `js/components/`)
        * editor.css, tinyMCE_config.js (see [tinyMCE](#tinymce))
    * images/ (theme preview image, icon, etc. - shown in the theme picker)
    * docs/ (optional, your own theme documentation)
    * php/
        * index.php (general theme functions, frontend only)
        * options.php (optional) manage theme options (frontend and backend)
        * xhr.php (optional) XHR routing file (frontend), see [Theme XHR endpoint](#theme-xhr-endpoint)
        * page-values.php / category-values.php (optional), see [Writing Additional Data](#writing-additional-data-php)
    * templates/ (home of your smarty template files, see [Templates](09-01-01-templates.md))
    * templates-mail/ (home of your mail templates, see [Mail templates](09-01-01-templates.md#mail-templates))
    * package.json, vite.config.js (optional - only if you build with Vite like the `default`
      theme does, see [Building the theme assets](#building-the-theme-assets))
    * info.xml (theme manifest: name, version, license, author, required core version)
    * readme.md (optional, parsed and shown in the ACP's theme editor and documentation browser)

## Building the theme assets {#building-the-theme-assets}

SwiftyEdit does not care how the files in `dist/` were produced - only that they exist under the
expected names. `head.tpl` links `dist/default.css` and `dist/theme.js` directly (and
`maintenance.tpl` does the same for `default`), and the tinyMCE integration expects
`dist/editor.css` and `dist/tinyMCE_config.js` (see [tinyMCE](#tinymce)). Beyond that
file/directory contract, using a build tool at all is entirely optional: you can hand-write plain
CSS and JS straight into `dist/`, use any bundler you prefer, or copy the setup described below -
it's your choice.

The `default` theme happens to build its assets with [Vite](https://vitejs.dev/) from source
files in `src/scss/` and `src/js/`. If you don't have a preference of your own, this is a
reasonable starting point to copy:

```
cd public/assets/themes/theme-name
npm install
npm run build   # one-off production build into dist/
npm run dev     # rebuilds into dist/ on every change (vite build --watch)
```

Its `vite.config.js` bundles `src/js/frontend.js` (plus everything it imports, including its
SCSS entry point `src/scss/default.scss`) into `dist/theme.js` and `dist/default.css`, running
Autoprefixer and cssnano on the CSS output. A small custom `copyAssets()` Vite plugin then copies
a few files into `dist/` __unprocessed__ (no Sass/PostCSS/bundling applied to them):

* `src/editor.css` → `dist/editor.css`
* `src/tinyMCE_config.js` → `dist/tinyMCE_config.js`
* the Bootstrap Icons webfonts → `dist/fonts/`

If you reuse this setup for a new theme, keep that distinction in mind: anything referenced from
`rollupOptions.input` in `vite.config.js` goes through the normal bundle pipeline, anything handled
by `copyAssets()` does not.

### Selecting a theme / template for a page

Which theme and layout template is actually used for a request is resolved in `app/smarty.php`,
roughly in this order:

1. The site-wide default theme and layout (`Settings → System`).
2. If the "user template" preference (`prefs_usertemplate`) is set to `on` or `overwrite`, a
   theme switcher can override this per session (`$_SESSION['prefs_template']` /
   `$_SESSION['prefs_template_stylesheet']`) - this is meant for theme developers to preview
   different themes/stylesheets without changing the site-wide setting.
3. If the page itself has a theme and layout assigned (`page_template`, `page_template_layout`
   - picked from a dropdown in the page editor sidebar, or left at the `use_standard` sentinel
   value to fall back to step 1/2), that takes precedence. `page_template_stylesheet` is also
   read here, but the page editor itself has no per-page stylesheet picker for it - only the
   global Themes admin page lets you pick a site-wide default stylesheet per theme.
4. If `prefs_usertemplate` is set to `overwrite` and the session theme (from step 2) ships a
   template file with the same name as the page's layout template, the session theme wins.

The page editor's layout dropdown is built by scanning every theme's `templates/` directory for
files matching `layout*.tpl` (`acp/core/pages/pages-edit.php`) and grouping the matches by
theme - so a theme is free to ship as many layouts as it wants (`layout_default.tpl`,
`layout_fullwidth.tpl`, `layout_landing.tpl`, ...) and each one shows up automatically, with no
extra registration step required. The same glob-per-file-prefix pattern is reused for the
site-wide default layout on the global Themes admin page, and, with `snippet*.tpl` instead of
`layout*.tpl`, for the template picker in the snippet editor.

Once `$se_template` is resolved, Smarty's template directory is set to
`[themes/{$se_template}/templates/, themes/default/templates/]` (in that order) - so any `.tpl`
file your theme doesn't provide is automatically loaded from the `default` theme instead. See
[Inheriting from the default theme](09-01-01-templates.md#inheriting-from-the-default-theme) for
what this means in practice, and where the same fallback does __not__ apply (your `dist/` CSS/JS).

## Writing Additional Data (PHP) {#writing-additional-data-php}

#### themes/theme-name/php/page-values.php

This file adds a **"Theme" tab** to the page editor.
This tab appears as soon as a page is saved with the `theme-name` theme.
The data is stored in the `page_template_values` column as JSON.
The data is read into the variable `$get_page['page_template_values']`.

Data is passed via the variable name `theme_values['..']` and automatically
stored in `page_template_values`.

```PHP
<?php
// themes/default/php/page-values.php
global $get_page;
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$page_template_data = json_decode($get_page['page_template_values'],true);
$page_template_teaser = html_entity_decode($page_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $page_template_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

#### themes/theme-name/php/category-values.php

Similar to the page extension, the **Category Editor** is extended here with a
"Theme" tab.
The data is stored in the `cat_template_values` column as JSON.
The data is read into the variable `$get_category['cat_template_values']`.

Data is passed via the variable name `theme_values['..']` and automatically
stored in `cat_template_values`.

```PHP
<?php
// themes/theme-name/php/category-values.php
global $get_category;
$category_template_data = json_decode($get_category['cat_template_values'],true);
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$category_teaser = html_entity_decode($category_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $category_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

## Theme XHR endpoint {#theme-xhr-endpoint}

`themes/theme-name/php/xhr.php` is where your theme handles its own AJAX/HTMX requests
(e.g. an `hx-get` in one of your templates). Requests to `/xhr/themes/{theme-name}/...` are
routed directly to this file (see `app/handlers/xhr-routes.php`) - there is __no further
built-in sub-routing__, so your file has to inspect the remaining path itself (e.g. via
`$requestPathParts`) to decide what to do:

```PHP
<?php
// themes/theme-name/php/xhr.php
// called for every request to /xhr/themes/theme-name/...
global $requestPathParts;

// example: /xhr/themes/theme-name/newsletter-signup/
if (($requestPathParts[3] ?? '') === 'newsletter-signup') {
    // handle the request, e.g. read $_POST, talk to the DB, echo a partial .tpl
}
```

The `default` theme ships an empty `php/xhr.php` stub - use it as your starting point if you
need one.

## Hooks {#hooks}

SwiftyEdit fires a small set of frontend hooks around page/product rendering (see
[Hooks](09-03-hooks.md) for the general hook mechanism and how plugins register callbacks).
The following ones are directly relevant to your templates - the full, authoritative list
always lives in `app/hooks/hooks-map.php`:

| Hook                      | Type   | Context                    | Relevant to templates because...                                                                 |
|---------------------------|--------|-----------------------------|----------------------------------------------------------------------------------------------------|
| `product.display.before`  | filter | `product_id`, `product`     | Runs before a product page is rendered; plugins may modify `$product_data`.                        |
| `product.display.actions` | filter | `product_id`, `product`     | Builds the `$product_plugin_actions` array assigned to `products-display.tpl` (see below).          |
| `product.display.after`   | action | `product_id`, `product`     | Fires after rendering (tracking, recommendations) - no template variables involved.                |
| `page.display.after`      | action | `page_data`, `query`        | Fires after any page is rendered - no template variables involved.                                  |

`product.display.actions` is the one you need to actually render: any plugin (the built-in
wishlist feature included) can push an entry onto `$product_plugin_actions`, and your
`products-display.tpl` must loop over it and render each entry according to its `type`. The
default theme's implementation looks like this:

```smarty
{foreach from=$product_plugin_actions item=action}
    {if $action.type == 'button'}
        <button type="submit" name="{$action.name|escape}" value="{$action.value|escape}"
                class="{$action.class|escape}">{$action.label|escape}</button>
    {elseif $action.type == 'button_htmx'}
        <button type="button" class="{$action.class|escape}"
                hx-get="{$action.hx_get|escape}&product_href={$product_href|escape:'url'}"
                hx-target="{$action.hx_target|escape}" hx-swap="{$action.hx_swap|escape}">
            {$action.label|escape}
        </button>
    {elseif $action.type == 'link'}
        <a class="{$action.class|escape}" href="{$action.href|escape}">{$action.label|escape}</a>
    {/if}
{/foreach}
```

If your theme replaces `products-display.tpl` entirely, you need to reproduce a loop like this
one, or plugin-provided product actions (including "Add to list") will silently not appear.

## Keeping the UI in sync: custom HX-Trigger events

Separately from the hooks above, several frontend XHR endpoints respond to a state-changing
request with an `HX-Trigger` response header naming one or more custom event(s) - this is plain
[HTMX](https://htmx.org/headers/hx-trigger/), not a SwiftyEdit-specific mechanism. Any element on
the page can react to one of these by adding it to its own `hx-trigger` attribute, typically like
this:

```smarty
<span id="shopping-cart-trigger" hx-get="/xhr/se/counter/?sc_items"
      hx-trigger="load, update_user_status from:body" hx-swap="innerHTML">0</span>
```

`load` renders it once up front; `{event} from:body` means "also re-run this request whenever
that event is dispatched on `<body>`" - `from:body` matters because the response that fires the
event and the element that should react to it are usually two completely unrelated parts of the
page. The events currently in use:

| Event                        | Fired by                                              | Used for                                      |
|-------------------------------|----------------------------------------------------------|-------------------------------------------------|
| `update_user_status`          | `login.php`, `wishlist.php`, `products.php`               | Header account/cart state (e.g. item count).    |
| `cart_item_added`              | `products.php`                                           | Cart icon bump animation - the one exception, listened for with plain JS (`document.body.addEventListener(...)` in `frontend.js`) instead of a declarative `hx-trigger`, since it drives a CSS animation rather than a re-fetch. |
| `update_wishlists`             | `wishlist.php` (create/rename/delete a list)              | The list picker/overview column.                |
| `update_wishlist_detail`       | `wishlist.php` (add/remove/reorder items in a list)        | A single list's detail view.                     |
| `update_comments`, `update_comment_posted` | `comments.php`                              | The comments block under a page/post.            |
| `update_votings_{id}`          | `ajax.votings.php` (`{id}` = the voted-on post/event id)   | That specific item's up/down vote counters - build the exact event name with the same id when listening. |
| `changed_password`             | `profile.php`                                             | The password tab on the profile page.            |
| `changed_mail_temp`            | `profile.php`                                             | The pending e-mail-change notice on the profile page. |
| `changed_avatar`               | `profile.php`                                             | The avatar preview on the profile page.          |

If your theme adds its own state-changing XHR actions, firing an `HX-Trigger` header the same way
lets any other part of the page (including elements added by other plugins) react to it without
you having to know who else needs to know.

## Custom Smarty modifiers

`app/smarty.php` registers a couple of native PHP functions as Smarty modifiers on top of what
Smarty ships by default: `|htmlentities`, `|strtolower` and `|trim`. The `trim` one matters in
particular - Smarty 5's `DefaultExtension` no longer includes a `trim` modifier out of the box,
so without this manual registration `{$var|trim}` would fail in your templates.

## Specifics

### tinyMCE {#tinymce}

A template is not only responsible for the appearance of your website,
but can also control the look and functions of the tinyMCE editor.
This way you can achieve that the WYSIWYG view is as close as possible
to the original layout (i.e. the frontend).

__Two files are largely relevant for this:__

* themes/{theme}/dist/editor.css
* themes/{theme}/dist/tinyMCE_config.js

The CSS file is used for the appearance of the content in the editor.
This is the easiest way to customize the editor to your layout.
The JavaScript file is used for configuration.
You can find more information in the tinyMCE documentation.

Further information on configuration can be found in the
[tinyMCE documentation](https://www.tiny.cloud/docs/tinymce/latest/)

### ACE editor

SwiftyEdit also bundles the ACE editor (`public/assets/editors/ace/`) as an alternative to
tinyMCE, with its own fixed set of syntax themes (`theme-chrome.js`, `theme-twilight.js`).
Unlike tinyMCE, there is currently no per-theme customization point (no `ace_config.js` or
equivalent CSS hook shipped in `dist/`) - ACE's appearance is not affected by your theme.
