# The template system
We use Smarty template system.
If you want to create your own template, you should be familiar with the smarty documentation.

## Good to know

* All themes are located in the `/public/assets/themes/` directory.
* The `administration` and `default` themes are overwritten on every update.
* Themes can extend the functionality of SwiftyEdit.

## Directory structure

* themes/theme-name/
    * dist/ (__required__: SwiftyEdit's templates link these files directly by name, see
      [Building the theme assets](#building-the-theme-assets) for how they get there)
        * core.css, core.js (always loaded)
        * shop.css, shop.js, events.css, comments.css, posts.css (optional components, see
          [Optional theme components](#optional-theme-components) - loaded only when selected)
        * editor.css, tinyMCE_config.js (see [tinyMCE](#tinymce))
        * fonts/ (only if your CSS needs them, e.g. the default theme's bootstrap-icons webfonts)
    * src/ (optional - only present if you build your assets from source; the `default` theme
      does this with Vite, see [Building the theme assets](#building-the-theme-assets))
        * scss/ (core entry point `core.scss`, mirrors the `js/` layout below: `scss/components/`
          holds one entry per optional component, e.g. `scss/components/shop.scss`; `scss/lib/`
          holds Sass partials imported by more than one entry, e.g. `scss/lib/_variables.scss`.
          A component's own styles live directly in its `scss/components/*.scss` entry - there's
          no separate per-component partial to keep in sync, since nothing else imports it)
        * js/ (core JS entry point `frontend.js`; `js/components/` holds one file per optional
          component, auto-discovered by `vite.config.js`, e.g. `js/components/shop.js`;
          `js/lib/` holds helper modules that entries import but that are not themselves
          components, e.g. `js/lib/wishlist.js`)
        * editor.css, tinyMCE_config.js (see [tinyMCE](#tinymce))
    * images/ (theme preview image, icon, etc. - shown in the theme picker)
    * docs/ (optional, your own theme documentation)
    * lang/ (optional, e.g. `de.json`, `en.json` - see
      [Translating your theme's ACP UI](#translating-your-themes-acp-ui))
    * php/
        * index.php (general theme functions, frontend only)
        * options.php (optional) manage theme options (frontend and backend)
        * xhr.php (optional) XHR routing file (frontend), see [Theme XHR endpoint](#theme-xhr-endpoint)
        * page-values.php / category-values.php (optional), see [Writing Additional Data](#writing-additional-data-php)
    * templates/ (home of your smarty template files, see [Templates](09-01-01-templates.md))
    * templates-mail/ (home of your mail templates, see [Mail templates](09-01-01-templates.md#mail-templates))
    * package.json, vite.config.js (optional - only if you build with Vite like the `default`
      theme does, see [Building the theme assets](#building-the-theme-assets))
    * info.json (theme manifest: name, version, author, description - see
      [The info.json file](#the-infojson-file))
    * poster.png / images/icon.png (optional, theme thumbnail shown in the theme picker)
    * readme.md (optional, parsed and shown in the ACP's theme editor and documentation browser)

## The info.json file {#the-infojson-file}

Every theme should have an `info.json` file in its root directory. It follows the same
structure as a [plugin's info.json](09-02-plugins.md#the-infojson-file), with `addon.type`
set to `theme` instead of `plugin`, and no `navigation` block (a theme's own backend UI is
its `php/options.php` file, reached from the fixed "Options" link on the Themes admin page -
not a list of nav entries).

```json
{
  "addon": {
    "id": "my-theme",
    "type": "theme",
    "name": "My Theme",
    "version": "1.0",
    "build": 1,
    "author": "Your Name",
    "description": "A short description of your theme",
    "update_url": "https://your-server.com/themes/my-theme/info.json"
  },
  "versions": [
    {
      "version": "1.0",
      "build": 1,
      "requires_build": "26-0183",
      "download_url": "https://your-server.com/themes/my-theme/my-theme-1.zip"
    }
  ]
}
```

As with plugins, only `name`, `version`, `author` and `description` are required for a theme
that's only ever installed manually. The remaining fields (`id`, `type`, `build`, `versions[]`,
`update_url`, `requires_build`) are only needed if you want your theme to be installable and
updatable from a URL through the ACP's "Install from URL" / catalog flow (see
[Plugins → The info.json file](09-02-plugins.md#the-infojson-file) for the full field
reference, allowed ZIP file types and update-check behavior - it applies to themes unchanged).

> **Legacy `info.xml`:** themes predating this format may still ship the older `info.xml`
> manifest (name, version, license, author, required core version) instead. SwiftyEdit reads
> it as a fallback when no `info.json` is present, so such a theme keeps showing up correctly
> in the ACP - but `info.xml` has no equivalent of `id`/`build`/`versions[]`/`update_url`, so a
> theme identified this way can never be installed/updated via URL. New themes should ship an
> `info.json` instead; `info.xml` is not read for anything but this fallback.

## Building the theme assets {#building-the-theme-assets}

SwiftyEdit does not care how the files in `dist/` were produced - only that they exist under the
expected names. `head.tpl` links `dist/core.css` and `dist/core.js` directly (and
`maintenance.tpl` does the same for `default`), and the tinyMCE integration expects
`dist/editor.css` and `dist/tinyMCE_config.js` (see [tinyMCE](#tinymce)). Beyond that
file/directory contract, using a build tool at all is entirely optional: you can hand-write plain
CSS and JS straight into `dist/`, use any bundler you prefer, or copy the setup described below -
it's your choice.

The `default` theme happens to build its assets with [Vite](https://vitejs.dev/) from source
files in `src/scss/` and `src/js/`. If you don't have a preference of your own, this is a
reasonable starting point to copy:

```
cd public/assets/themes/theme-name
npm install
npm run build   # one-off production build into dist/
npm run dev     # rebuilds into dist/ on every change (vite build --watch)
```

Its `vite.config.js` declares one fixed `rollupOptions.input` entry, `core` (from
`src/js/frontend.js`, importing the `core.scss` entry point), plus one entry per file it finds in
`src/js/components/` - a small `discoverComponentEntries()` helper `fs.readdirSync()`s that
folder so adding a new [optional component](#optional-theme-components) is just "add a file",
no `vite.config.js` edit. Each component entry imports its own SCSS entry point (e.g.
`src/scss/components/shop.scss`, holding that component's actual style rules directly - there's
no separate per-component partial, since nothing else would import it) and, where relevant, its
own JS. Helper modules that an entry imports but that are not themselves components
(`theme_switch.js`, `wishlist.js`) live in `src/js/lib/` instead - anything directly under
`src/js/components/` becomes its own component, so a helper module placed there by mistake would
incorrectly show up as one. Vite names each entry's output after its input key
(`core.css`/`core.js`, `shop.css`/`shop.js`, ...) and runs Autoprefixer and cssnano on all CSS
output. Component SCSS entries only pull in Bootstrap's functions/variables/maps
(`src/scss/lib/_bootstrap-vars.scss`), not the full compiled Bootstrap CSS - that already ships
once in `core.css` - so keep that in mind if you add another component: importing the full
`bootstrap` partial from a component entry would duplicate all of Bootstrap's CSS into that
component's bundle. A small custom `copyAssets()` Vite plugin then copies a few files into
`dist/` __unprocessed__ (no Sass/PostCSS/bundling applied to them):

* `src/editor.css` → `dist/editor.css`
* `src/tinyMCE_config.js` → `dist/tinyMCE_config.js`
* the Bootstrap Icons webfonts → `dist/fonts/`

If you reuse this setup for a new theme, keep that distinction in mind: anything referenced from
`rollupOptions.input` in `vite.config.js` goes through the normal bundle pipeline, anything handled
by `copyAssets()` does not.

### Optional theme components {#optional-theme-components}

The `default` theme splits its shop/events/comments/posts styling (and the shop's JS - wishlist
sorting, the quantity stepper, the price range slider) out of the always-loaded core bundle into
their own `dist/shop.{css,js}`, `dist/events.css`, `dist/comments.css` and `dist/posts.css`
files, so a page that doesn't use a given feature area doesn't ship its CSS/JS. Everything that's
global (jQuery, Bootstrap's JS, htmx, GLightbox, the dark-mode switcher, the page header/footer)
stays in `core.css`/`core.js` and is always loaded.

Nothing about *which* components exist is hardcoded anywhere in PHP or Smarty - it's derived
purely from a naming convention on `dist/`, in `php/theme-components.php`:

> Every `dist/<id>.css` and/or `dist/<id>.js` file is one selectable component named `<id>` (a
> component doesn't need both files - CSS-only or JS-only is fine), except a short reserved list
> (`core`, `editor`, `tinyMCE_config`) that are not optional components.

`se_theme_component_ids($theme_dist_dir)` returns the sorted list of ids found this way, and
`se_theme_component_has_css()`/`se_theme_component_has_js()` check which of the two files a given
id actually has (an empty placeholder file, like the `default` theme's CSS-only components ship
as their `.js` entry, does not count - see [Building the theme
assets](#building-the-theme-assets) for why they exist at all). Because discovery reads `dist/`
rather than `src/`, it works no matter how (or whether) a theme is built with Vite - hand-written
`dist/newsletter.css` with no source step behind it is discovered exactly the same way. This also
means adding a component to the `default` theme is genuinely just "drop a file, rebuild": no
`page-values.php`, `options.php` or `head.tpl` edit needed, only (optionally) a
`label_component_<id>` key in `lang/*.json` for a nicer picker label - see [Translating your
theme's ACP UI](#translating-your-themes-acp-ui). Without one, the picker falls back to the raw,
capitalized id.

Which components load for a given page is a per-page choice, made in the page editor's "Theme"
tab (`php/page-values.php`, using `theme-components.php` to build the checkbox list - see
[Writing Additional Data](#writing-additional-data-php)) and stored in `page_template_values`
next to the teaser text, under the keys `components_mode` (`"all"` or `"custom"`) and
`comp_<id>` (`"1"` when enabled, one per discovered id). Pages saved before this option existed
have no `components_mode` key, which is treated the same as `"all"` - so existing pages keep
loading everything, exactly like the old single-bundle build did.

To make that page-level choice available on the frontend, `app/template-setup.php` decodes
`page_template_values` into a `$theme_values` array before your theme's `php/options.php` runs -
any theme's `options.php` can read `$theme_values['your_key']` for whatever it stored via
`page-values.php`, not just for component loading. The `default` theme's `options.php` runs the
same `theme-components.php` discovery again and turns it into a `$se_theme_components` array
keyed by id (`['shop' => ['enabled' => bool, 'has_css' => bool, 'has_js' => bool], ...]`)
assigned to Smarty, which `head.tpl` then loops over to decide which `<link>`/`<script>` tags to
print - no component names appear in the template either:

```smarty
{foreach $se_theme_components as $component_id => $component}
    {if $component.enabled && $component.has_css}
        <link rel="stylesheet" media="screen" href="{$se_inc_dir}/themes/{$se_template}/dist/{$component_id}.css" />
    {/if}
{/foreach}
```

If you build your own theme with several optional feature areas, this whole pattern is a
reasonable one to copy: drop `theme-components.php` in alongside your own `page-values.php` and
`options.php`, let `src/js/components/` (if you use Vite) or your own build step decide what ends
up in `dist/`, and loop over `$se_theme_components` in your templates instead of naming
components anywhere.

### Color variants (stylesheets) {#color-variants-stylesheets}

Besides the layout, a theme can also offer several color variants without having to ship several
complete themes for it - the "Stylesheet" dropdown on the global Themes admin page
(`/admin/addons/`), right next to the layout picker. The convention is deliberately similar to
the [optional theme components](#optional-theme-components) above, just with a fixed
subdirectory instead of a reserved name list:

> Every `dist/skins/<name>.css` file is one selectable color variant named `<name>`.

`acp/core/addons/data-reader.php` scans this folder to build the dropdown; the label is the
filename without its extension, capitalized (`ocean.css` → "Ocean") - unlike components, there's
currently no `lang/*.json` translation key for it. The selected variant is printed as an
additional `<link>` __after__ `dist/core.css`, but only if your theme does that in its own
`head.tpl` - this isn't a core automatism, here's how the `default` theme does it:

```smarty
<link rel="stylesheet" media="screen" href="{$se_inc_dir}/themes/{$se_template}/dist/core.css" />
{if $se_template_stylesheet != ''}
	<link rel="stylesheet" media="screen" href="{$se_inc_dir}/themes/{$se_template}/dist/skins/{$se_template_stylesheet}" />
{/if}
```

`$se_template_stylesheet` is already assigned to Smarty whenever a variant is active - site-wide
setting, session override, or page override, see the precedence chain below under [Selecting a
theme / template for a page](#selecting-a-theme-template-for-a-page).

The ACP mechanism and `$se_template_stylesheet` itself are theme-independent - any theme can ship
`dist/skins/*.css` and print a `<link>` for it in its own `head.tpl`. How the `default` theme
actually __builds__ these files, though, is its own Vite-specific pattern and not required for
your own theme:

* `src/scss/skins/*.scss` is auto-discovered (`discoverSkinEntries()` in `vite.config.js`, the
  same idea as `discoverComponentEntries()` for the components above) and each file compiles
  independently to `dist/skins/<name>.css`. Files with a leading underscore
  (`_skin-tokens.scss`) count as a Sass partial and are skipped - they're meant to be imported,
  not built standalone.
* `src/scss/skins/_skin-tokens.scss` provides a `skin-tokens($primary, $primary-dark: null)`
  mixin that derives the full set of CSS custom properties `core.scss` exposes for skinning from
  a single color: `--bs-primary(-rgb)`, `--bs-link-color(-rgb)`, `--bs-link-hover-color(-rgb)`,
  Bootstrap's own "subtle/emphasis" tokens (`--bs-primary-text-emphasis`/`-bg-subtle`/
  `-border-subtle`), `--bs-body-bg`/`-color`, `--bs-border-color`, `--bs-heading-color`, plus the
  theme's own `--se-header-bg`/`--se-footer-bg`/`--se-navbar-bg`/`--se-teaser-bg`/
  `--se-widget-bg`. A simple variant only needs one line as a result:
  ```scss
  @import "skin-tokens";
  @include skin-tokens(#1d7a8c);
  ```
* That list is enough because most Bootstrap components already read colors from CSS custom
  properties at runtime (links, `.bg-/.text-/.border-primary`, `.alert-primary` via the subtle
  tokens) - a handful of "solid" components bake their color in as a literal hex value at Sass
  compile time instead (`.btn-primary`, `.btn-outline-primary`, `.pagination`, `.list-group`,
  `.nav-pills`, `.form-check-input`, `.table-primary`). `core.scss` re-points exactly those onto
  `var(--bs-primary)` (some via `color-mix()` for hover/active shades), so a variant doesn't have
  to chase down every individual Bootstrap component by hand.
* For a punchier, less formulaic result, a variant can override the mixin's own gradient/navbar/
  footer/dark-surface values instead of relying purely on the automatic derivation - see the two
  bundled examples, `ocean.scss` and `sunset.scss`. This especially pays off for warm hues
  (orange/red): just darkening and desaturating a color reads as brown almost immediately (that's
  perceptually what brown *is*) - `sunset.scss` deliberately shifts its navbar, footer and every
  dark surface towards a blue-violet tone instead, the same way an actual sunset photo's dark
  areas (night sky, deep water) are blue-violet, not dark orange.

### Selecting a theme / template for a page {#selecting-a-theme-template-for-a-page}

Which theme and layout template is actually used for a request is resolved in `app/smarty.php`,
roughly in this order:

1. The site-wide default theme and layout (`Settings → System`).
2. If the "user template" preference (`prefs_usertemplate`) is set to `on` or `overwrite`, a
   theme switcher can override this per session (`$_SESSION['prefs_template']` /
   `$_SESSION['prefs_template_stylesheet']`) - this is meant for theme developers to preview
   different themes/stylesheets without changing the site-wide setting.
3. If the page itself has a theme and layout assigned (`page_template`, `page_template_layout`
   - picked from a dropdown in the page editor sidebar, or left at the `use_standard` sentinel
   value to fall back to step 1/2), that takes precedence. `page_template_stylesheet` is also
   read here, but the page editor itself has no per-page stylesheet picker for it - only the
   global Themes admin page lets you pick a site-wide default stylesheet per theme.
4. If `prefs_usertemplate` is set to `overwrite` and the session theme (from step 2) ships a
   template file with the same name as the page's layout template, the session theme wins.

The page editor's layout dropdown is built by scanning every theme's `templates/` directory for
files matching `layout*.tpl` (`acp/core/pages/pages-edit.php`) and grouping the matches by
theme - so a theme is free to ship as many layouts as it wants (`layout_default.tpl`,
`layout_fullwidth.tpl`, `layout_landing.tpl`, ...) and each one shows up automatically, with no
extra registration step required. The same glob-per-file-prefix pattern is reused for the
site-wide default layout on the global Themes admin page, and, with `snippet*.tpl` instead of
`layout*.tpl`, for the template picker in the snippet editor.

Once `$se_template` is resolved, Smarty's template directory is set to
`[themes/{$se_template}/templates/, themes/default/templates/]` (in that order) - so any `.tpl`
file your theme doesn't provide is automatically loaded from the `default` theme instead. See
[Inheriting from the default theme](09-01-01-templates.md#inheriting-from-the-default-theme) for
what this means in practice, and where the same fallback does __not__ apply (your `dist/` CSS/JS).

## Translating your theme's ACP UI {#translating-your-themes-acp-ui}

Any strings your theme prints into the __ACP__ (its `php/options.php` fields on the theme's
"Options" page, or a `page-values.php`/`category-values.php` tab like the one below) can be
translated the same way plugins do it: a flat key/value JSON file per language in `lang/`
(`lang/de.json`, `lang/en.json`, ...). Load it with `se_return_addon_translations($theme_id,
'theme')` (the same function plugins use via `se_return_addon_translations($plugin_id)` -
themes just pass `'theme'` as the second argument so it looks under `SE_THEMES` instead of
`SE_PLUGINS`). It reads the file matching the current admin session's language and falls back
to `lang/en.json` if that file doesn't exist - a theme doesn't need to cover every language
SwiftyEdit ships, just the ones you want to support:

```PHP
<?php
// themes/theme-name/php/page-values.php
$theme_lang = se_return_addon_translations('theme-name', 'theme');
echo '<h5>'.$theme_lang['title_theme_values'].'</h5>';
```

```json
// themes/theme-name/lang/en.json
{
  "title_theme_values": "Theme Values"
}
```

This function is only defined in the ACP (`acp/core/functions_addons.php`, autoloaded for every
admin request) - it does not exist on the frontend, so don't call it from `templates/*.tpl` or
your theme's frontend-facing PHP. Frontend strings go through the regular `$lang` array/language
pack instead (see the language pack files under `languages/`).

## Writing Additional Data (PHP) {#writing-additional-data-php}

#### themes/theme-name/php/page-values.php

This file adds a **"Theme" tab** to the page editor.
This tab appears as soon as a page is saved with the `theme-name` theme.
The data is stored in the `page_template_values` column as JSON.
The data is read into the variable `$get_page['page_template_values']`.

Data is passed via the variable name `theme_values['..']` and automatically
stored in `page_template_values`.

```PHP
<?php
// themes/default/php/page-values.php
global $get_page;
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$page_template_data = json_decode($get_page['page_template_values'],true);
$page_template_teaser = html_entity_decode($page_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $page_template_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

#### themes/theme-name/php/category-values.php

Similar to the page extension, the **Category Editor** is extended here with a
"Theme" tab.
The data is stored in the `cat_template_values` column as JSON.
The data is read into the variable `$get_category['cat_template_values']`.

Data is passed via the variable name `theme_values['..']` and automatically
stored in `cat_template_values`.

```PHP
<?php
// themes/theme-name/php/category-values.php
global $get_category;
$category_template_data = json_decode($get_category['cat_template_values'],true);
echo '<h5>Theme Values <small>(Theme: theme-name)</small></h5>';
$category_teaser = html_entity_decode($category_template_data['teaser_text'], ENT_QUOTES | ENT_XML1, 'UTF-8');
$input_wysiwyg_page_teaser = [
    "input_name" => "theme_values[teaser_text]",
    "input_value" => $category_teaser,
    "label" => 'Teaser Text',
    "type" => "textarea",
    "mode" => "wysiwyg"
];
echo se_print_form_input($input_wysiwyg_page_teaser);
```

## Theme XHR endpoint {#theme-xhr-endpoint}

`themes/theme-name/php/xhr.php` is where your theme handles its own AJAX/HTMX requests
(e.g. an `hx-get` in one of your templates). Requests to `/xhr/themes/{theme-name}/...` are
routed directly to this file (see `app/handlers/xhr-routes.php`) - there is __no further
built-in sub-routing__, so your file has to inspect the remaining path itself (e.g. via
`$requestPathParts`) to decide what to do:

```PHP
<?php
// themes/theme-name/php/xhr.php
// called for every request to /xhr/themes/theme-name/...
global $requestPathParts;

// example: /xhr/themes/theme-name/newsletter-signup/
if (($requestPathParts[3] ?? '') === 'newsletter-signup') {
    // handle the request, e.g. read $_POST, talk to the DB, echo a partial .tpl
}
```

The `default` theme ships an empty `php/xhr.php` stub - use it as your starting point if you
need one.

## Hooks {#hooks}

SwiftyEdit fires a small set of frontend hooks around page/product rendering (see
[Hooks](09-03-hooks.md) for the general hook mechanism and how plugins register callbacks).
The following ones are directly relevant to your templates - the full, authoritative list
always lives in `app/hooks/hooks-map.php`:

| Hook                      | Type   | Context                    | Relevant to templates because...                                                                 |
|---------------------------|--------|-----------------------------|----------------------------------------------------------------------------------------------------|
| `product.display.before`  | filter | `product_id`, `product`     | Runs before a product page is rendered; plugins may modify `$product_data`.                        |
| `product.display.actions` | filter | `product_id`, `product`     | Builds the `$product_plugin_actions` array assigned to `products-display.tpl` (see below).          |
| `product.display.after`   | action | `product_id`, `product`     | Fires after rendering (tracking, recommendations) - no template variables involved.                |
| `page.display.after`      | action | `page_data`, `query`        | Fires after any page is rendered - no template variables involved.                                  |
| `image.variants`          | filter | `src`, `widths`, `ratio`, `fit` | Lets a plugin supply responsive `src`/`srcset` variants for the `{img}` tag (see [below](#responsive-images-with-img)) - without one, `{img}` still renders a plain `<img src>`. |

`product.display.actions` is the one you need to actually render: any plugin can push an entry
onto `$product_plugin_actions`, and your `products-display.tpl` must loop over it and render each
entry according to its `type`. The built-in wishlist "Add to list" button is *not* wired through
this filter - it's a core feature and is rendered from its own dedicated template variables
(`$show_wishlist_button`, `$wishlist_logged_in`, `$wishlist_already_saved`, `$wishlist_login_uri`,
assigned in `app/handlers/products-display.php`) so it can sit right next to the "add to cart"
button instead of wherever plugin actions happen to render. The default theme's implementation of
the plugin-actions loop looks like this:

```smarty
{foreach from=$product_plugin_actions item=action}
    {if $action.type == 'button'}
        <button type="submit" name="{$action.name|escape}" value="{$action.value|escape}"
                class="{$action.class|escape}">{$action.label|escape}</button>
    {elseif $action.type == 'link'}
        <a class="{$action.class|escape}" href="{$action.href|escape}">{$action.label|escape}</a>
    {/if}
{/foreach}
```

If your theme replaces `products-display.tpl` entirely, you need to reproduce a loop like this
one, or plugin-provided product actions will silently not appear.

## Keeping the UI in sync: custom HX-Trigger events

Separately from the hooks above, several frontend XHR endpoints respond to a state-changing
request with an `HX-Trigger` response header naming one or more custom event(s) - this is plain
[HTMX](https://htmx.org/headers/hx-trigger/), not a SwiftyEdit-specific mechanism. Any element on
the page can react to one of these by adding it to its own `hx-trigger` attribute, typically like
this:

```smarty
<span id="shopping-cart-trigger" hx-get="/xhr/se/counter/?sc_items"
      hx-trigger="load, update_user_status from:body" hx-swap="innerHTML">0</span>
```

`load` renders it once up front; `{event} from:body` means "also re-run this request whenever
that event is dispatched on `<body>`" - `from:body` matters because the response that fires the
event and the element that should react to it are usually two completely unrelated parts of the
page. The events currently in use:

| Event                        | Fired by                                              | Used for                                      |
|-------------------------------|----------------------------------------------------------|-------------------------------------------------|
| `update_user_status`          | `login.php`, `wishlist.php`, `products.php`               | Header account/cart state (e.g. item count).    |
| `cart_item_added`              | `products.php`                                           | Cart icon bump animation - the one exception, listened for with plain JS (`document.body.addEventListener(...)` in `frontend.js`) instead of a declarative `hx-trigger`, since it drives a CSS animation rather than a re-fetch. |
| `update_wishlists`             | `wishlist.php` (create/rename/delete a list)              | The list picker/overview column.                |
| `update_wishlist_detail`       | `wishlist.php` (add/remove/reorder items in a list)        | A single list's detail view.                     |
| `update_comments`, `update_comment_posted` | `comments.php`                              | The comments block under a page/post.            |
| `update_votings_{id}`          | `ajax.votings.php` (`{id}` = the voted-on post/event/product id) | That specific item's up/down vote counters - build the exact event name with the same id when listening. |
| `update_guestlist_{id}`        | `ajax.guestlist.php` (`{id}` = the event id)               | The confirmed-guests counter on the event detail page - only relevant when the count is set to public. |
| `changed_password`             | `profile.php`                                             | The password tab on the profile page.            |
| `changed_mail_temp`            | `profile.php`                                             | The pending e-mail-change notice on the profile page. |
| `changed_avatar`               | `profile.php`                                             | The avatar preview on the profile page.          |

If your theme adds its own state-changing XHR actions, firing an `HX-Trigger` header the same way
lets any other part of the page (including elements added by other plugins) react to it without
you having to know who else needs to know.

## Custom Smarty modifiers

`app/smarty.php` registers a couple of native PHP functions as Smarty modifiers on top of what
Smarty ships by default: `|htmlentities`, `|strtolower` and `|trim`. The `trim` one matters in
particular - Smarty 5's `DefaultExtension` no longer includes a `trim` modifier out of the box,
so without this manual registration `{$var|trim}` would fail in your templates.

## Embedding plugins directly with {plugin} {#embedding-plugins-directly-with-plugin}

`app/smarty.php` also registers `{plugin}` as a Smarty block function
(`se_smarty_block_plugin()` in `app/functions/func_basics.php`). It's the template counterpart to
the `[plugin=name]query[/plugin]` shortcode editors use in content fields (see
[Plugins → When are which plugin files loaded?](09-02-plugins.md#when-are-which-plugin-files-loaded))
- both paths run through the same `buffer_script()` function internally, so they behave
identically:

```smarty
{plugin name="example-plugin"}foo=bar{/plugin}
```

| Attribute | Required | Meaning |
|-----------|----------|---------|
| `name`    | yes      | Directory name of the plugin under `/plugins/`, same as with the `[plugin=...]` shortcode. |

The block content (`foo=bar` in the example) corresponds to the query between `[plugin=...]`
and `[/plugin]` and is parsed the same way (`parse_str()`) - every `name=value` pair you pass is
available inside the plugin as a PHP variable of the same name.

Unlike the content-field shortcode, `{plugin}` is a regular part of the template and gets
compiled by Smarty like anything else - so the block content may also contain template
variables:

```smarty
{plugin name="example-plugin"}foo={$product.foo}{/plugin}
```

Use `{plugin}` when your theme wants to hard-wire a plugin call into its markup (e.g. always
showing a particular form in the footer) without going through an editor-managed snippet or page
content.

## Responsive images with {img} {#responsive-images-with-img}

`app/smarty.php` also registers `{img}` as a Smarty function (`app/functions/functions.img.php`).
It always renders *something*: a plain `<img src="...">` if no image-processing plugin is active,
or an `<img srcset="..." sizes="...">` with responsive width variants if one is (e.g. the bundled
`image-resizer` plugin). Your theme never needs to know which case applies - adopt `{img}` today
and get responsive/optimized images for free the moment a plugin is active, with no template
change required either way:

```smarty
{img src="{$product.image}" widths="400,800,1200" ratio="4:3" fit="cover"
     sizes="(max-width: 600px) 100vw, 800px" alt="{$product.title|escape}" loading="lazy"}
```

| Attribute | Required | Meaning |
|-----------|----------|---------|
| `src`     | yes      | Image path, e.g. `/images/foo.jpg` (the existing public upload path). |
| `widths`  | no       | Comma-separated target widths in px, one `srcset` entry each. Omit it and `{img}` renders a plain `<img src>` even with a plugin active - no variants are generated unless you ask for them. |
| `ratio`   | no       | Target aspect ratio, e.g. `4:3`. |
| `fit`     | no       | `cover` (crop-fill, default) or `contain` (whole image visible, no crop). |
| `sizes`   | no       | Passed straight through to the `sizes` attribute - a pure layout decision, never computed by `{img}` or a plugin. |
| `alt`, `class`, `id`, `loading`, `title` | no | Passed straight through to the rendered `<img>` tag. |
| `width`, `height` | no | Passed straight through if you set both. If you set neither, `{img}` fills them in itself from `ratio` (when a crop was requested) or the original file's own dimensions (when it wasn't) - never a guess, so the declared aspect ratio always matches what's actually served. This reserves the correct layout space before the image loads (avoids layout shift/CLS) without risking a mismatched ratio that would visually stretch/squash the image. |

Core owns this attribute contract and the plain-`<img>` fallback, not any plugin - so the contract
stays stable even if you later switch which image-processing plugin is active. What a plugin *can*
do is hook the `image.variants` filter (see the Hooks table above) to turn `widths`/`ratio`/`fit`
into an actual `src`/`srcset`; format negotiation (AVIF/WebP/JPEG) happens per request via the
`Accept` header at that point, not via a `<picture>` element.

## Specifics

### tinyMCE {#tinymce}

A template is not only responsible for the appearance of your website,
but can also control the look and functions of the tinyMCE editor.
This way you can achieve that the WYSIWYG view is as close as possible
to the original layout (i.e. the frontend).

__Two files are largely relevant for this:__

* themes/{theme}/dist/editor.css
* themes/{theme}/dist/tinyMCE_config.js

The CSS file is used for the appearance of the content in the editor.
This is the easiest way to customize the editor to your layout.
The JavaScript file is used for configuration.
You can find more information in the tinyMCE documentation.

Further information on configuration can be found in the
[tinyMCE documentation](https://www.tiny.cloud/docs/tinymce/latest/)

### ACE editor

SwiftyEdit also bundles the ACE editor (`public/assets/editors/ace/`) as an alternative to
tinyMCE, with its own fixed set of syntax themes (`theme-chrome.js`, `theme-twilight.js`).
Unlike tinyMCE, there is currently no per-theme customization point (no `ace_config.js` or
equivalent CSS hook shipped in `dist/`) - ACE's appearance is not affected by your theme.
