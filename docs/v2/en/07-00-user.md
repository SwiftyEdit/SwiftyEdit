# User management

<kbd>Backend</kbd> ▶ <kbd>User</kbd>

There are two ways in which user accounts can be created.
Users can register themselves independently via the frontend
(if this function is enabled in the settings), or the user account is created via the backend.

If a user registers via the frontend,
he has to confirm his account. I.e., he must click the confirmation link,
which is automatically sent to his e-mail address.

## The (user) rights management

SwiftyEdit has effective rights management for visitors, moderators and administrators.

Each user or administrator can be equipped with different user rights.
The individual options can be found under <kbd>User</kbd> ▶ <kbd>Edit user</kbd> ▶
<kbd>Password</kbd>, where the rights checkboxes are managed alongside the password.

## Two-factor authentication {#two-factor-authentication}

With two-factor authentication (2FA), logging in to the backend needs a second factor in
addition to the password: a code by e-mail or from an authenticator app. A stolen or guessed
password alone is then no longer enough to take over the site.

2FA only applies to the backend login (`/admin/`). Frontend accounts (e.g. customers) log in
as before. Administrators who log in through the frontend only get a regular user session -
backend rights are only granted by the backend login.

### Enabling 2FA {#2fa-enable}

2FA is disabled by default. It is enabled for **all** backend users at once, with one line in
`data/config.php` (see [Developer](09-00-developer.md)):

```php
<?php
// data/config.php
$se_2fa_required = true;
```

It deliberately can't be switched in the backend settings - a hijacked backend session must
not be able to turn the protection off.

As soon as 2FA is enabled, everybody who hasn't set it up yet is guided through the setup at
their next login. Backend users can also set it up beforehand in their personal settings (see
below), so nobody is surprised by the switch. While 2FA is off, the dashboard shows a hint
that can be hidden.

### Methods {#2fa-methods}

Each user chooses one of two methods during the setup:

* __Authenticator app__ (recommended) - an app on the phone, e.g. Aegis, 2FAS, Google or
  Microsoft Authenticator, shows a new 6-digit code every 30 seconds. To set it up, scan the
  QR code or type in the key shown below it. The app works offline and doesn't depend on
  e-mails. The QR code is created in the browser; no external service is involved.
* __Code by e-mail__ - a 6-digit code is sent with every login. It is valid for 10 minutes and
  can only be used once. This method depends on working mail delivery - check that e-mails
  from SwiftyEdit arrive before you rely on it. The setup only completes once a code has
  arrived and been entered.

### Recovery codes {#2fa-recovery-codes}

At the end of the setup, SwiftyEdit shows 10 recovery codes (e.g. `4F7K-9QX2`). Each of them
replaces the code from the app or the e-mail **once** - for when the phone is lost or e-mails
don't arrive. The codes are only shown this one time: print them or store them in a password
manager. New codes can be created in the personal settings; the old ones stop working then.

### Trust this device {#2fa-trusted-devices}

After entering the code, you can tick **Trust this device for 30 days**. On this browser, the
login then only asks for the password. The password is always required - a trusted device
only skips the second factor.

Trusted devices are listed in the personal settings and can be removed there. They are also
removed automatically when the password changes or 2FA is set up again.

### Personal settings {#2fa-personal-settings}

<kbd>User menu</kbd> (top right) ▶ <kbd>Settings</kbd>

Every backend user manages their own 2FA here:

* set it up (also before 2FA is enabled for the site),
* set it up again / change the method,
* create new recovery codes,
* see and remove trusted devices,
* disable it - only possible while 2FA is not required in `data/config.php`.

Changes need the password and a current code (or a recovery code).

### User management {#2fa-user-management}

In the user list, a shield icon shows who has 2FA set up. Administrators with the right to
manage users can **reset** 2FA for another user on the edit page - for example when someone has
lost both the phone and the recovery codes. The setup then starts again at that user's next
login. Your own 2FA can't be reset there; use the personal settings instead.

### Emergencies {#2fa-emergencies}

| Situation | Solution |
|---|---|
| Phone lost, or e-mails don't arrive | log in with a recovery code |
| Phone and recovery codes lost, other administrators exist | another administrator resets 2FA for you |
| You are the only administrator and have no access at all | emergency switch in `data/config.php` |

The emergency switch skips 2FA for **one** user until a given date and time (in the timezone
of the site settings):

```php
<?php
// data/config.php - emergency: skip 2FA for this user until the given date
$se_2fa_bypass = ['user' => 'admin', 'until' => '2026-12-31 12:00'];
```

While it is set, the dashboard shows a warning. After logging in, open the personal settings
and choose **Set up again / change method** - while the emergency switch is active for your
account, your password is enough to confirm it. Then remove the line right away.

### Good to know {#2fa-notes}

* The keys of the authenticator apps are stored encrypted. The key for this comes from the file
  `data/site_secret.php`, which SwiftyEdit creates on its own. Keep it private, and include it
  in your backups of the `data` directory - if it gets lost, the app setups stop working and
  have to be set up again (use a recovery code or the emergency switch to log in).
* Changes to `data/config.php` can take up to a minute to take effect if the server caches PHP
  files (OPcache).
* Wrong codes are limited: after 5 wrong codes, the login starts again with the password.
